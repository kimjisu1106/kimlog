## 요약

복합 업무용 빌딩의 공식 사이트와 회의실 예약 시스템을 하나로 묶은 웹 애플리케이션이다. 공개 사이트 여섯 개 섹션과 운영자용 관리 콘솔로 이루어져 있다.

등장하는 로그스톤 빌딩은 가상 브랜드다. 실제 건물이나 기업과 관계없고, 입주사·매장·연락처도 전부 지어낸 것이다.

구성은 Vite + React 19 + TypeScript로 화면을 만들고, Cloudflare Workers 위의 Hono가 API와 검색용 메타 태그 주입을 맡는다. 데이터는 D1에, 관리자가 올린 이미지는 R2에 둔다.

---

## 제작 동기

어느 빌딩에서 회의실을 운영하는 실무자에게 이야기를 들었다. 사이트에 뭔가 고칠 게 생기면 제작 업체에 요청하고 기다려야 하는데 회신이 느리다고 했다.

무엇이 불편한지 물어 목록을 받았고, 그게 그대로 만들 것의 목록이 됐다. 회의실을 실제로 운영하는 사람이 겪는 문제라 추측할 필요가 없었다.

실제로 쓰는 사람이 겪는 문제를 그대로 목록으로 받아 화면까지 만들어 보는 것이 목적이었다. 기능 명세를 상상해서 쓰는 것과, 매일 그 일을 하는 사람이 짚어 준 것을 만드는 것은 결과가 다르다.

---

## 목표 설정

받은 불편 다섯 가지를 그대로 목표로 삼았다.

- 시간대별 예약이 안 돼서 회의실 하나에 하루 한 건만 잡힌다. 나머지 신청은 엑셀로 따로 관리하는데, 두 장부가 어긋나면 같은 시간에 두 팀이 들어오는 사고가 난다
- 관리자가 예약을 고칠 수 없어서 취소하고 다시 잡아야 한다. 그 사이에 다른 사람이 자리를 채갈 수도 있다
- 다섯 개 회의실의 예약 현황이 한눈에 안 보인다
- 요금표나 이용안내 같은 문구를 고치려면 업체에 요청해야 한다
- 입점업체 이미지와 로고도 업체를 거쳐야 한다

여기에 스스로 건 조건이 하나 있다. 원본을 그대로 베끼면 저작권 문제가 되고, 너무 다르게 만들면 개선안으로 읽히지 않는다. 정보구조만 남기고 코드와 문구는 새로 쓰기로 했다.

## 주요 작업

### 30분 단위 시간대 예약

09:00부터 18:00까지를 30분 슬롯으로 쪼갰다. 중복은 애플리케이션 검사가 아니라 데이터베이스 제약으로 막는다. 점유 슬롯을 별도 테이블에 한 행씩 넣고 회의실·날짜·슬롯에 복합 기본키를 걸었다.

```sql
CREATE TABLE reservation_slots (
  room_id        INTEGER NOT NULL,
  date           TEXT    NOT NULL,
  slot_min       INTEGER NOT NULL,
  reservation_id INTEGER NOT NULL REFERENCES reservations(id) ON DELETE CASCADE,
  PRIMARY KEY (room_id, date, slot_min)
);
```

예약 행과 슬롯을 한 트랜잭션으로 넣기 때문에, 두 사람이 같은 순간에 같은 시간대를 신청하면 뒤에 도착한 요청이 통째로 롤백된다. 동시성 처리를 코드가 아니라 스키마가 책임진다. 엑셀을 따로 둘 이유가 사라진다.

### 취소 없이 예약 수정

관리자가 시간·회의실·신청 내용을 그 자리에서 고친다. 기존 슬롯 해제와 새 슬롯 점유가 한 트랜잭션이라, 옮기려는 자리가 이미 차 있으면 이동만 실패하고 원래 예약이 그대로 남는다. 예약번호도 유지된다.

### 하루치를 한 화면에 보는 타임라인

다섯 개 회의실의 하루를 한 화면에 놓았다. 승인 대기와 승인 완료가 색으로 갈리고, 빈 칸을 누르면 전화 접수를 바로 등록한다. 위쪽 주간 스트립은 일요일부터 토요일까지 일곱 칸을 항상 세워, 예약이 없는 날도 건수 0으로 보인다.

### 저장 → 미리보기 → 배포

문구와 사진을 관리자가 직접 고치되, 실수가 바로 라이브로 나가지 않게 세 단계를 뒀다.

| 단계 | 동작 | 공개 사이트 |
| --- | --- | --- |
| 저장 | 초안만 갱신 | 그대로 |
| 미리보기 | 초안을 입힌 실제 화면 확인 (로그인한 관리자만) | 그대로 |
| 배포 | 초안을 발행본으로 승격 | 즉시 반영 |

외부 빌드를 부르지 않아 배포 버튼을 누르면 1초 안에 반영된다. 편집 화면은 페이지마다 따로 만들지 않았다. 필드 정의 하나로 폼이 생성되게 해서 페이지를 늘려도 관리자 화면이 따라온다.

### 이미지 관리

홈 캐러셀, 갤러리, 회의실 사진, 입주사·매장 로고를 관리자가 직접 올리고 바꾼다. 이미지 교체도 위의 세 단계를 그대로 탄다. 파일 이름을 내용의 해시로 지어, 같은 파일을 다시 올려도 하나만 저장되고 캐시를 영구로 걸어도 낡은 그림이 남지 않는다.

기본 제공 이미지는 코드와 함께 배포되는 정적 자산에 둬서, 저장소 설정 없이도 데모가 그림까지 다 찬다. 사진은 저작권 표기 의무가 없는 CC0만 골라 썼고, 로고가 없는 입주사는 이름에서 뽑은 이니셜을 그린다.

### 그 밖에

- 검색과 공유 카드를 위해 Worker가 경로별 제목·설명·OG 태그를 HTML에 주입한다. 크롤러와 메신저 봇은 자바스크립트를 실행하지 않는다
- 본문 폰트를 자체 호스팅하되 한글 상용 범위로 잘라 2MB를 436KB로 줄였다
- 실제 브라우저를 열어 전 화면의 렌더링과 콘솔 오류를 확인하는 검사를 붙였다

## 결과

공개 사이트 여섯 개 섹션과 관리자 콘솔이 돌아가고, 2026년 9월에 공개 주소로 배포했다. 위에 적은 다섯 가지 목표는 전부 구현했다.

검증은 세 겹이다. 타입 검사, API 전 구간 점검 92개, 실제 브라우저로 전 화면을 여는 검사 217개.

가상 브랜드라 검색 색인은 막아 뒀다. 링크로 들어가면 공개 사이트를 둘러볼 수 있고, 푸터의 "관리자 콘솔 둘러보기" → "구경용으로 둘러보기" 두 번을 누르면 운영자 화면까지 들어간다. 구경용 계정은 화면을 다 보되 바꾸는 요청을 서버가 거절한다.

| 항목 | 상태 |
| --- | --- |
| 시간대별 예약 · 중복 차단 | 완료 |
| 취소 없이 예약 수정 | 완료 |
| 예약 현황 타임라인 | 완료 |
| 콘텐츠 저장 → 미리보기 → 배포 | 완료 |
| 이미지 직접 교체 | 완료 |
| 관리자 화면 다듬기 | 완료 |
| 회의실 좌석 배치도 | 완료 |
| 조작 이력 · 사업자등록증 첨부 | 완료 |
| 예약 승인·반려 안내 메일 | 완료 (메일 앱 초안) |
| 공개 배포 | 완료 |

안내 메일은 담당자의 기본 메일 앱을 받는 사람·제목·본문이 채워진 채로 여는 방식이다. 서버가 직접 보내려면 건물 운영사 도메인을 발신 등록해야 해서, 그건 실제로 쓰기로 정해진 뒤에 할 일로 남겼다.

넘길 때의 절차는 저장소의 `HANDOVER.md`에 따로 정리했다. 클라우드 계정과 도메인을 고객 명의로 새로 만들고 그 위에 다시 구축하는 것이 기본이고, 지금 배포된 것은 제안용이라 그대로 넘기지 않는다.

코드 저장소는 비공개다. 화면과 동작은 위 링크에서 그대로 볼 수 있다.
