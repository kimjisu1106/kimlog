## 막힌 부분

- 제품 페이지 데모 건반이 옛 사각형 모양으로 남았다
	- 원인: 제품 페이지의 움직이는 데모는 앱 그리기 코드를 옮겨 온 사본이라 앱을 바꿔도 따라가지 않는다. 파동 때 「바꾸면 데모 값도 보낸다」고 정해 놓고 모션에만 해당된다고 좁게 적어서, 건반을 바꾼 이번엔 빠뜨렸다. 샵이 먼저 짚었다
	- 해결: 바뀐 건반 그리기 파일을 통째로 넘겼다. 건반이나 파티클 그리기를 바꾼 릴리스는 체크리스트에 「샵 데모 코드 전달」까지 넣었다

### 편집툴 테스트로 원인을 확정했다

어젯밤 만들어 둔 테스트 파일을 편집툴에서 열어 239프레임(두 번째 키프레임 직전)을 봤다.

- A 같은 데이터를 MP4로 다시 포장만 → 깨짐
- B 다른 인코더(x264)로 재압축 → 정상
- C 멀쩡한 B를 앱과 같은 AMD 설정으로 재압축 → 깨짐
- D A의 데이터는 그대로 두고 파일 머리 정보만 통일 → 정상
- E AMD 인코더에 B프레임 켜기 → 정상

479프레임(세 번째 키프레임 직전)은 전부 정상이었다. 데이터를 한 바이트도 안 바꾼 D가 멀쩡하니 원인은 파일 머리의 SPS(영상 전체 설정을 담은 정보)가 영상 안 SPS와 다른 것이다.

앱이 하드웨어 인코더를 쓰는 건 속도 때문이다. 소프트웨어로 압축하면 한 프레임에 100밀리초가 넘게 걸리던 게 몇 밀리초로 준다. 대신 칩 제조사마다 만든 인코더라 출력 구조가 표준에서 조금씩 벗어날 수 있고, 이번처럼 너그러운 도구에선 안 보이다가 엄격한 프로그램에서 드러난다. 속도를 얻은 만큼 호환성 확인이 따라붙는다.

D와 E 중에서 D 방식을 골랐다. E는 AMD 칩마다 B프레임 지원이 달라 다른 PC에서 실패할 수 있고, D는 인코더와 상관없이 머리만 정리한다.

- 해결: 인코더가 MP4 대신 원시 H.264 스트림을 쓰고, 추출이 끝나면 MP4로 다시 감싼다. 앱으로 다시 뽑은 영상이 편집툴에서 정상인 것까지 확인했다

### 원시 스트림을 감싸다 오디오가 통째로 빠졌다

원시 H.264 스트림에는 프레임마다 시각 정보가 없다. 이걸 오디오와 한 번에 MP4로 합치니 영상 길이를 0.38초로 잘못 읽어, 짧은 쪽에 맞춰 자르는 옵션(`-shortest`)이 오디오를 통째로 버렸다. 영상 트랙은 멀쩡하게 나와서 영상만 확인하면 놓친다.

시각을 만드는 옵션도 골라야 했다. `-framerate`로 주면 마이크로초 반올림이 쌓여 키프레임이 4초에 80µs씩 밀리고, 입력에 `-r`로 주면 정확히 떨어진다.

```bash
# 1) 원시 스트림 → 영상만 든 MP4 (시각은 입력 -r로)
ffmpeg -r 60 -i out.video.h264 -c:v copy out.video.mp4
# 2) 그 MP4에 오디오를 붙인다 (이제 영상 길이를 읽을 수 있다)
ffmpeg -i out.video.mp4 -i audio.wav -map 0:v -map 1:a -c:v copy -c:a aac -b:a 192k -shortest out.mp4
```

- 해결: 두 단계로 나눴다. 결과는 키프레임이 정확히 0/4/8초, 오디오가 0초에 같이 시작하고, 파일 머리와 영상 안의 SPS가 같다
- 남은 규칙: 출력 방식을 바꾸면 영상 한 장면만 보지 말고 결과 파일 전체(오디오 트랙·길이·시작 시각)를 확인한다
