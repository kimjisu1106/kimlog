## 오늘 한 일

샵이 판매 페이지를 넘어 여러 프로젝트의 정책 허브가 된 날.

- KeyBloom 제품 페이지 하단에 접이식 업데이트 내역(Changelog)을 추가함 — 빌드할 때 GitHub 릴리스 목록을 읽어 정적으로 굽고, 최신 3개만 보이다가 "이전 버전 보기"로 펼친다
- 릴리스 노트 하나에 한국어·영어를 함께 적고 구분선으로 가르는 규약을 정해, 샵이 로케일에 맞는 쪽만 보여주게 함
- 릴리스가 없거나 불러오기에 실패하면 섹션 자체를 숨김 — 에러를 고객에게 노출하지 않는다
- 완성 문서로 관리하던 Privacy·Terms를 조항 단위 데이터로 분리함 — 조항마다 적용 제품 태그가 붙고, 페이지는 태그로 걸러 조립된다
	- 이유: 제품마다 데이터 관행이 달라(결제·게임 재화·파일 처리) 스토어에 "그 앱 얘기만 있는" 문서를 내야 했고, 공통 조항 수정이 문서마다 흩어지는 것도 막고 싶었다
- 통합본(`/privacy/`·`/terms/`)은 유지하고 제품별 페이지(`/{제품}/privacy/` 등)를 같은 소스에서 뽑음 — 하루 만에 제품 7종(keybloom·metronome·sandrop·office-layout·kimlog·pawbit 포함) 등록
- 정책 URL 표준 규칙 확정 — 앱·스토어의 정책 URL은 자기 제품 정책을 쓰고, 블로그 URL은 앱에 쓰지 않는다. 새 앱 출시 절차에 제품 정책 등록이 포함됨
- 블로그(kimlog)도 정책 시스템에 편입 — 범위는 블로그 사이트와 웹 도구까지로 경계를 그음
- 프로젝트마다 담당 Claude 세션이 따로라 조율이 사용자를 거쳐야 했는데, 저장소에 요청함 파일(INBOX.md)을 만들어 세션들이 직접 요청·회신을 주고받게 함
- 가동 첫날 성적: 요청 4건(KeyBloom 조항 검수, 여둘까 광고 고지 누락, 메트로놈 하드웨어 조항, Pawbit 신규 등록) + 공지 2건(블로그 정책 의존 설문, 자율 확인 룰) 처리 — 7개 세션 전원이 자율 확인 룰을 자기 문서에 채택
- 밤에는 블로그 로스터에서 샵 등록 후보를 검토 — 자체 IP 유틸(Duplicate Finder)은 손질 후 등록으로 백로그에 올리고, 타인 IP 팬메이드 2종은 사업자 스토어 진열 비추로 판정

## 막힌 부분

- 다른 세션이 조율 없이 조항 파일을 직접 고쳐 문서에 아동 섹션이 두 번 들어감
	- 해결: 검수로 병합하고, "조항 직접 수정 금지 — 요청은 INBOX로" 규약을 세움
- 공통 조항에 업체 이름을 열거했더니 제품별 페이지에 무관한 업체명이 샘
	- 해결: 공통 조항은 "제3자 서비스"처럼 일반화한다는 규칙을 문서에 박음 — 조립형 문서의 함정
- 블로그 편입을 두고 하루 안에 분리 확정 → 무단 편입 반려 → 사용자 승인으로 번복이 오감
	- 해결: "사이트+웹 도구만 편입, 모바일 앱 고지는 각 제품 정책이 담당" 경계로 착지 — 반려 사유를 경계 조건으로 바꾼 셈
- 여러 세션이 같은 저장소를 동시에 만져 응답 줄이 다른 커밋에 묻힘
	- 해결: "고치기 전 pull, 고친 뒤 즉시 push"를 요청함 규칙에 추가
