## 배포와 자동화

### 배포 방식은 프로젝트를 만들 때 정해지고 나중에 못 바꾼다

호스팅에 올리는 방법이 두 가지였다. 내 컴퓨터에서 명령을 돌려 결과물을 밀어 넣는 방식과, 저장소를 연결해 두고 코드를 올리면 호스팅이 알아서 빌드하는 방식이다.

먼저 명령 방식으로 붙였다가 연결 방식으로 옮기려 했는데, 이게 프로젝트를 만들 때만 고를 수 있는 항목이었다. 옮기려면 프로젝트를 지우고 다시 만들어야 하고, 그러면 주소도 놓쳤다가 다시 잡아야 한다.

처음 만들 때 한 번 묻고 지나가는 선택이 되돌리기 제일 비싼 선택인 경우가 있다. 도구를 처음 쓸 때는 "이건 나중에 바꿀 수 있나"를 먼저 확인하는 게 낫다.

### 명령으로 올리는 흐름

연결 방식으로 가기 전까지는 이렇게 올렸다. 지금도 호스팅 빌드가 막혔을 때의 우회로로 남겨 뒀다.

```bash
# 프로젝트를 한 번 만들고
wrangler pages project create todo-openday --production-branch main

# 이후로는 빌드 결과 폴더를 올린다
wrangler pages deploy dist --project-name todo-openday
```

### 자동 배포 파일의 뼈대

중간에 자동 배포를 직접 만들어 붙였다. 결국 걷어냈지만 구조는 알아두면 쓸 데가 있다. 언제 돌지, 어떤 컴퓨터에서, 무슨 단계를 밟을지를 적는 것이 전부다.

```yaml
on:
  push:
    branches: [main]

jobs:
  deploy:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v5
      - uses: actions/setup-node@v5
        with:
          node-version: 22
      - run: npm ci
      - run: npm run build
```

### 남이 만든 단계에도 버전이 있고 수명이 있다

위의 `actions/checkout@v5`처럼 남이 만들어 둔 단계를 가져다 쓰는데, 여기에도 버전이 있다. 처음에 `@v4`를 썼더니 경고가 떴다 — 그 버전이 도는 Node 20을 실행 환경이 더 이상 지원하지 않는다는 내용이었다.

우리 코드가 아니어도 낡는다. 경고가 뜨면 무시하지 말고 버전을 올리는 게 맞다.

### 토큰은 저장소에 두지 않고 주입한다

자동 배포가 호스팅에 접근하려면 열쇠가 필요한데, 이걸 코드에 적으면 저장소를 보는 사람 누구나 쓸 수 있다. 저장소 설정에 값을 넣어 두고 실행할 때만 꺼내 쓴다.

```yaml
      - run: npx wrangler pages deploy dist
        env:
          CLOUDFLARE_API_TOKEN: ${{ secrets.CLOUDFLARE_API_TOKEN }}
```

코드에는 "이 이름의 비밀값을 가져와라"만 적히고 실제 값은 안 남는다.

### 자격증명이 없으면 배포 전에 멈추고 이유를 남긴다

비밀값을 넣기 전에 돌렸더니 그냥 실패했다. 도구가 "그럼 로그인하자"로 넘어갔는데 실행 환경에는 브라우저가 없으니 알아볼 수 없는 오류만 남았다.

그래서 배포를 시도하기 전에 먼저 확인하고, 없으면 사람이 읽을 문장으로 멈추게 했다.

```yaml
      - name: Check credentials
        run: |
          if [ -z "${{ secrets.CLOUDFLARE_API_TOKEN }}" ]; then
            echo "::error::저장소 Secrets에 토큰이 없습니다"
            exit 1
          fi
```

실패는 어차피 나지만 왜 실패했는지 알려주는 실패가 훨씬 싸다.

### 빌드하는 쪽의 Node 버전을 파일로 고정한다

내 컴퓨터에서는 되는데 호스팅에서 빌드가 깨질 수 있다. 빌드 도구가 요구하는 Node 버전보다 낮은 환경일 수 있어서다. 설정 화면에서 환경변수로 정할 수도 있지만, 파일로 두면 저장소를 옮겨도 따라간다.

```text
22
```

`.nvmrc`라는 이름의 파일에 버전 숫자만 적으면 호스팅이 읽어 간다.

### push와 배포를 붙일지 뗄지

같은 계열의 다른 프로젝트에서는 일부러 떼어 놓았다. `git push`는 백업이고, 실제 사이트 반영은 별도 명령이다. 실험 중인 코드가 밀어 넣는 것만으로 라이브에 나가지 않게 하려는 것이다.

이 프로젝트에서는 붙였다. 쓰는 사람이 가족 한 명이고 고치는 주기가 짧아서, 매번 두 번 손대는 비용이 사고 위험보다 컸다. 대신 빌드에 타입 검사를 넣어 두어서 타입이 어긋나면 배포가 멈춘다.

정답이 있는 게 아니라 쓰는 사람이 몇 명이고 실수했을 때 무엇을 잃느냐로 갈린다.

### 정식 서비스는 배포용 브랜치를 따로 둔다

지금은 붙여 뒀지만, 낯선 사람이 쓰기 시작하면 이 구조는 위험해진다. 그때는 배포 대상을 `main`이 아니라 `release`로 옮기고, `main`은 개발이 모이는 자리로 내린다.

바꿀 때 고칠 곳까지 문서에 적어 뒀다. 나중에 급할 때 찾아 헤매지 않으려는 것이다.

## 검색 엔진에서 감추기

### 감추는 방법이 세 가지고 성격이 다르다

| 방법 | 하는 일 |
| --- | --- |
| 크롤러 안내 파일 | 들어오지 마라 (크롤링 차단) |
| 페이지 안의 표시 | 읽어도 되지만 목록에 넣지 마라 (색인 차단) |
| 응답 헤더의 표시 | 위와 같되 모든 파일에 적용 |

### 크롤링을 막으면 색인 금지를 못 읽는다

흔히 안내 파일에 "전부 막음"을 적는데, 이게 역효과가 난다. 못 들어오게 하면 페이지 안에 적어 둔 "목록에 넣지 마세요"를 읽을 방법이 없다. 그래서 다른 곳에 링크가 걸려 있으면 내용 없이 주소만 검색 결과에 남는 일이 생긴다.

들어와서 읽게 두되 색인만 막는 쪽이 맞다.

### 헤더로 거는 쪽이 더 확실하다

페이지 안의 표시는 HTML을 읽어야 알 수 있다. 헤더는 파일 종류를 가리지 않고 모든 응답에 붙는다.

```text
/*
  X-Robots-Tag: noindex, nofollow
```

Cloudflare Pages는 결과물 폴더 최상단의 `_headers` 파일을 읽어 응답 헤더를 붙여 준다. `/*`는 모든 주소라는 뜻이다.

## 크기 계산에서 밟은 것들

### 100vw는 스크롤바를 포함하고 100%는 아니다

가게 폭을 "화면 폭 빼기 96px"로 잡았는데 가로 스크롤바가 생겼다. 세로 내용이 길어 세로 스크롤바가 먼저 생긴 게 시작이었다.

화면 폭을 뜻하는 `100vw`는 스크롤바 두께까지 포함한 값이다. 세로 스크롤바가 15px을 차지하면 실제로 쓸 수 있는 폭은 `100vw - 15px`인데, 계산은 그걸 모르고 돌아간다.

반면 부모를 기준으로 하는 `100%`는 스크롤바를 뺀 값이다. 그래서 가운데 정렬 계산을 이렇게 바꿨다.

```css
.street-track {
  /* 100vw로 하면 스크롤바 두께만큼 어긋난다 */
  padding-left: calc((100% - var(--shop-w)) / 2);
}
```

### height 100%는 사슬이라 중간이 끊기면 통째로 무시된다

높이를 화면에 맞추려고 여러 번 고쳤는데 두 번 다 안 나았다. 계산식은 처음부터 맞았고 기준점이 없던 게 원인이었다.

높이를 비율로 지정하려면 부모가 자기 높이를 알고 있어야 한다. 중간에 하나라도 "내용만큼"인 요소가 있으면 그 아래의 비율 지정은 기준을 잃고 무시된다. React는 `#root`라는 상자 안에 그리는데 그 상자에 높이를 안 줬던 것이다.

```css
html,
body,
#root {
  height: 100%;
}
```

식을 의심하기 전에 기준점부터 봤어야 했다.

### 세로 가운데 정렬과 넘침 숨김을 같이 쓰면 위쪽이 잘린다

내용이 화면보다 길어졌을 때, 가운데 정렬은 넘친 만큼을 위아래로 반씩 밀어낸다. 아래로 넘치면 스크롤해서 볼 수 있지만 위로 넘친 것은 볼 방법이 없다. 넘침까지 숨겨 두면 그대로 사라진다.

증상은 "맨 위에 있는 것부터 없어진다"로 나타난다. 우리 경우엔 상단 탭이었다.

화면을 꽉 채우는 배치에서는 세로 가운데 정렬을 쓰지 않는 게 안전하다. 위에서부터 채우면 넘쳐도 아래로만 넘친다.

### min-height 0을 사슬 각 단계에 (어제 배운 것의 발전형)

어제 "세로로 쌓은 flex는 공간이 모자라면 자식을 줄인다"를 배웠는데, 오늘은 그 반대 방향을 밟았다. flex 자식은 내용보다 작아지지 않는 게 기본이라, 안쪽에 스크롤 영역을 두려면 각 단계에서 풀어줘야 한다.

```css
.shop,
.board,
.board-scroll {
  min-height: 0;
}
```

한 단계라도 빠지면 그 지점에서 막혀 내용이 스크롤 대신 밖으로 밀려난다. 스크롤이 안 될 때 넘침 설정부터 보게 되는데, 실제 원인은 이쪽인 경우가 많다.

### 구간별 고정값 사다리 대신 계산식으로

처음엔 화면 크기 구간마다 값을 따로 적었다. 1400px 이하면 얼마, 1200px 이하면 얼마 하는 식이다. 구간이 늘어날수록 어디를 고쳐야 할지 헷갈리고, 구간 사이에서는 어차피 어정쩡하다.

계산식 하나로 바꾸니 사다리가 통째로 사라졌다.

```css
:root {
  /* 화면을 채우되 양옆 여백을 남기고, 아주 넓으면 1200에서 멈춘다 */
  --shop-w: min(1200px, calc(100vw - 96px));
}
```

구간을 나누는 건 값이 불연속으로 달라져야 할 때만 쓰면 된다. 우리 경우엔 그냥 따라오면 되는 값이었다.

### max로 음수 여백 막기

모바일에서 가게 폭을 화면 폭과 같게 했더니 가운데 여백 계산이 0이나 음수가 됐다. 음수 여백은 요소를 바깥으로 밀어내서 배치를 망가뜨린다.

```css
padding: 12px max(0px, calc((100% - var(--shop-w)) / 2)) 20px;
```

계산으로 나오는 값에는 바닥을 정해 두는 게 안전하다.

## 스크롤바 꾸미기

### 굵기와 색은 상속되고 모양은 안 된다

스크롤바를 꾸미는 방법이 두 갈래다. 파이어폭스 계열은 굵기와 색만 정할 수 있고, 크롬 계열은 막대 모양까지 정할 수 있다. 그런데 두 방식의 성격이 다르다.

```css
/* 상속되는 속성이라 부모에 한 번만 적으면 안쪽까지 닿는다 */
.shop {
  scrollbar-width: thin;
  scrollbar-color: #d3c5aa transparent;
}

/* 이쪽은 상속되지 않아 자손 선택자로 따로 건다 */
.shop ::-webkit-scrollbar {
  width: 12px;
}
```

처음엔 스크롤되는 곳마다 셀렉터를 여섯 개씩 나열하고 있었다. 상속되는 걸 알고 나니 부모 한 곳으로 줄었고, 나중에 스크롤 영역이 새로 생겨도 자동으로 같은 모양이 된다.

### 투명 테두리로 막대에 여백 주기

막대를 얇게 만들면서 클릭 영역은 남기고 싶었다. 테두리를 투명으로 주고 배경이 안쪽까지만 칠해지게 하면, 폭 12px 중 실제로 보이는 막대는 6px이 된다.

```css
.shop ::-webkit-scrollbar-thumb {
  border: 3px solid transparent;
  background: #d3c5aa;
  background-clip: content-box;
  border-radius: 999px;
}
```

`background-clip: content-box`가 없으면 테두리 자리까지 배경이 칠해져서 여백이 생기지 않는다.

### 트랙은 투명이 안전하다

막대가 지나가는 홈을 종이색으로 고정했더니 메모 입력칸에서만 홈이 드러났다. 그 칸의 배경색이 살짝 달랐기 때문이다. 투명으로 두니 어디에 놓여도 그 자리 배경을 그대로 비춘다.

배경이 한 가지가 아닌 곳에서는 색을 맞추는 것보다 비우는 게 낫다.

## 광고 붙이기

### 광고 자리를 먼저 잡아 둔다

광고는 스크립트가 나중에 채운다. 자리를 안 잡아 두면 광고가 들어오는 순간 그만큼 화면이 아래로 밀리고, 누르려던 버튼이 손가락 밑에서 이동한다.

그래서 스크립트를 붙이기 전에 규격 크기만 먼저 잡아 뒀다.

```css
.ad-slot {
  width: 728px;
  height: 90px;
}

@media (max-width: 767px) {
  .ad-slot {
    width: 320px;
    height: 50px;
  }
}
```

### 로더는 실행 시점에 있는 자리만 채운다

광고 스크립트는 실행될 때 페이지를 훑어 자리를 찾아 채운다. 그래서 화면 크기가 바뀌어 규격이 달라지고 자리를 새로 그리면, 스크립트도 다시 실행해야 광고가 들어온다.

```tsx
useEffect(() => {
  const script = document.createElement('script')
  script.src = '//t1.kakaocdn.net/kas/static/ba.min.js'
  script.async = true
  document.body.appendChild(script)
  return () => script.remove()
}, [ad.unit])
```

규격이 바뀔 때마다 옛 스크립트를 떼고 새로 붙인다.

### 자리는 숨긴 채로 시작한다

광고 자리를 처음부터 보이게 두면, 광고가 안 채워졌을 때 빈 칸이 그대로 보인다. 그래서 숨긴 채로 두고 광고 쪽이 채운 뒤에 직접 보이게 바꾸도록 맡긴다.

```tsx
<ins
  className="kakao_ad_area"
  style={{ display: 'none' }}
  data-ad-unit={ad.unit}
/>
```

### 개발 중에는 진짜 광고를 부르면 안 된다

이게 제일 중요했다. 화면을 고치며 수십 번 새로고침하는데 그때마다 노출이 잡히면 무효 트래픽이 된다. 사람이 보지도 않은 광고가 노출로 집계되는 것이라 광고 계정이 위험해진다.

```tsx
const live = import.meta.env.PROD
```

배포본에서만 진짜 광고를 부르고, 개발 중에는 점선 상자만 보이게 했다.

### 화면 크기 변화를 구독해 규격 바꾸기

데스크톱용과 모바일용을 둘 다 그려놓고 하나를 숨기는 방법도 있지만, 안 보이는 쪽도 노출로 잡힐 수 있다. 그래서 맞는 것 하나만 그리고, 창 크기가 바뀌면 다시 고른다.

```tsx
const [isMobile, setIsMobile] = useState(
  () => window.matchMedia('(max-width: 767px)').matches,
)

useEffect(() => {
  const query = window.matchMedia('(max-width: 767px)')
  const onChange = (e: MediaQueryListEvent) => setIsMobile(e.matches)
  query.addEventListener('change', onChange)
  return () => query.removeEventListener('change', onChange)
}, [])
```

CSS 미디어쿼리와 같은 값을 써야 자리와 광고가 어긋나지 않는다.

## React에서 더 배운 것

### 화면 크기를 상태로 다루기

위의 코드가 그 예다. 초기값은 지금 상태를 한 번 읽어서 정하고, 그 뒤로는 변화를 구독한다. 창 크기 변화를 매번 다시 계산하는 방식과 달리, 기준선을 넘을 때만 알려 주므로 가볍다.

### 자동 저장 표시의 타이밍

글자를 칠 때마다 저장되는 구조라 "저장됨"을 매번 띄우면 계속 깜빡인다. 손이 멈춘 뒤 잠깐 떴다 사라지게 했다.

```ts
function markSaved(key: string) {
  window.clearTimeout(settle.current)
  setSavedKey(null)
  settle.current = window.setTimeout(() => setSavedKey(key), 600)
}
```

타자 중에는 타이머가 계속 취소되다가, 멈추면 600ms 뒤에 한 번 뜬다.

표시가 뜰 때 줄이 밀리지 않게 자리는 항상 차지하고 보이기만 바뀌게 했다. 글 쓰는 중에 화면이 움찔하면 그게 더 거슬린다.

### 배포본에서만 도는 코드 나누기

`import.meta.env.PROD`와 `DEV`로 갈라 두면 배포본에는 아예 안 실린다. 개발용 초기화 버튼, 광고 자리 안내 표시 같은 것을 이걸로 감쌌다.

디버그용 화면을 "나중에 지우자"고 남겨 두면 반드시 잊는다. 처음부터 안 나가게 묶는 게 낫다.

### 눌러서 고치는 인라인 편집

일회성 업무는 제목을 눌러 그 자리에서 고친다. 평소엔 글자고 누르면 입력칸으로 바뀐다.

```tsx
{editingId === t.id ? (
  <input
    value={t.title}
    autoFocus
    onChange={(e) => onRename(t.id, e.target.value)}
    onBlur={() => setEditingId(null)}
    onKeyDown={(e) => e.key === 'Enter' && setEditingId(null)}
  />
) : (
  <button onClick={() => setEditingId(t.id)}>{t.title}</button>
)}
```

`autoFocus`가 있어야 바뀌자마자 바로 칠 수 있고, 다른 곳을 클릭하거나 Enter를 치면 끝난다.

## 도구를 다루다 낸 사고

### 파일 목록을 뒷부분만 보면 앞이 잘린다

여러 사람이 같이 쓰는 파일을 없는 줄 알고 새로 써서 남의 내용을 지웠다. 원인은 목록을 확인할 때 뒷부분만 보는 방식을 쓴 것이었다. 찾던 파일이 정렬상 앞쪽에 있어서 화면에 안 나왔다.

목록을 훑을 때 잘리는 방식을 쓰면 "없다"와 "안 보인다"를 구별할 수 없다. 있는지 확인하는 게 목적이면 이름으로 걸러 봐야 한다.

### 도구가 "만들었다"가 아니라 "고쳤다"고 하면 멈춰야 한다

파일을 쓴 뒤 도구가 돌려준 문구가 "created"가 아니라 "updated"였다. 그때 이상하다고 느꼈는데, 파일 생성 시각이 방금으로 찍힌 걸 보고 "새로 만든 게 맞다"고 넘어갔다.

덮어쓰기는 생성 시각을 다시 찍을 수 있으므로 그건 증거가 못 됐다. 도구가 준 신호가 예상과 다르면 그 신호가 이긴다.

### 규칙보다 구조로 막는 게 낫다

같은 사고가 이틀 연속 났다. "파일 전체를 새로 쓰지 말고 자기 부분만 추가한다"는 규칙을 적어도, 이번 실수는 그 규칙을 어긴 게 아니라 파일이 있는 줄 몰랐던 것이다. 규칙은 "몰랐다"를 못 막는다.

프로젝트마다 파일을 나눠 쓰면 충돌이 구조적으로 불가능해진다. 지킬 것을 늘리는 대신 지킬 일이 없게 만드는 쪽이 강하다.

## 판단으로 배운 것

### 광고를 붙이면 방침이 따라와야 한다

광고는 광고 식별자를 쓴다. 그러니까 광고를 붙이는 순간 개인정보처리방침이 필요해진다. 순서가 거꾸로 되면 안 되는 종류의 일이다.

이 앱은 계정도 없고 기록도 브라우저에만 있어서 수집하는 게 전혀 없었는데, 광고 하나 때문에 방침이 생겼다. 기능을 붙일 때 따라오는 게 코드만이 아니다.

### 링크가 아직 없으면 404 대신 안내로

방침 주소를 받기 전에 관리 화면을 먼저 만들었다. 링크를 살려두면 눌렀을 때 없는 페이지가 뜬다.

```tsx
if (!url) {
  return <span className="doc-link--pending">{label} 준비 중</span>
}
```

주소 상수가 비어 있으면 안내로, 채워지면 링크로 바뀐다. 나중에 주소가 나왔을 때 고칠 곳은 한 줄이었다.

### 백로그에는 할 일과 함께 이유를 적는다

할 일만 적어 두면 나중에 볼 때 "이걸 왜 하기로 했더라"가 된다. 그러면 그때 기분으로 순서를 다시 정하게 된다.

이유를 같이 적어 두면 우선순위가 저절로 서고, 상황이 바뀌었을 때 "이 이유가 아직 유효한가"로 판단할 수 있다.

### 같은 요소를 화면마다 다르게 하면 나중에 설명이 안 된다

스크롤바를 기록실만 감췄다가, 오늘 화면도 감췄다가, 결국 넷 다 보이게 하고 모양을 통일했다. 각 단계마다 그럴듯한 이유가 있었는데 모아 놓고 보니 일관성이 없었다.

화면마다 다르게 할 이유가 있다면 그 이유를 한 문장으로 적을 수 있어야 한다. 못 적겠으면 그냥 같게 하는 게 맞다.
