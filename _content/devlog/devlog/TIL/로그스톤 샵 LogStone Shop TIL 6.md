## 정책 문서의 배포 순서

### 앱보다 방침이 먼저 라이브여야 한다

스토어 심사는 앱이 실제로 하는 일과 개인정보처리방침 본문을 대조한다. 구글 플레이의 데이터 보안(Data safety) 양식도 마찬가지라, 양식에 "계정 식별자를 처리한다"고 적어놓고 방침에 그 얘기가 없으면 반려 사유가 된다.

그래서 순서는 이렇게 된다.

1. 기능이 무엇을 어디로 보내는지 확정
2. 방침·약관 조항을 쓰고 배포 (URL이 살아 있어야 한다)
3. 그 문구에 맞춰 데이터 보안 양식 작성
4. 앱 빌드 업로드

기능이 먼저 나가면 심사 기간 내내 방침과 어긋난 상태가 된다. 코드가 준비돼도 문서가 안 됐으면 출시를 미루는 게 맞다.

### 기능이 나가면 소개 문구도 같이 나간다

제품 소개에 "가입도 로그인도 없습니다"라고 적어 뒀는데 다음 버전에 선택형 구글 로그인이 들어간다. 방침만 고치고 소개 문구를 두면, 방침은 맞고 마케팅 문구는 틀린 상태가 된다.

한 사실이 여러 자리에 흩어져 있으면 기능이 바뀔 때 전부 같이 움직여야 한다. 지금은 자리를 기억해 두고 출시 시점에 함께 바꾸는 수준으로 관리하지만, 자리가 늘면 문구도 데이터로 빼서 한 곳에서 바꾸는 편이 낫다.

## 선택형 클라우드 기능을 방침에 쓰기

### 권한 범위는 이름 그대로 적는다

"구글 계정으로 로그인한다"는 설명은 방침에서는 부족하다. 앱이 실제로 요구하는 권한 범위(scope)를 이름 그대로 적어야 이용자가 무엇에 동의하는지 확인할 수 있다.

```text
games_lite      플레이 게임즈 기본 기능 (플레이어 ID 수준)
drive.appdata   앱이 만든 파일만 접근 — 이용자의 다른 드라이브 파일은 볼 수 없다
```

`drive.appdata`가 중요한 이유는 저장 위치가 이용자 본인의 드라이브라는 점이다. 우리 서버가 데이터를 받는 게 아니라 이용자 계정 안에 저장되고, 우리는 그 내용을 열람할 수도 보관할 수도 없다. 방침에는 이 구분을 분명히 적었다.

### 철회·삭제 방법을 적는다

수집 항목만 적고 끝내면 안 된다. 이용자가 스스로 되돌릴 방법이 있어야 하고, 그 경로를 방침에 써야 한다.

- 연결하지 않아도 앱은 그대로 동작한다(선택 기능)
- 계정 연결을 해제하는 방법
- 이미 올라간 데이터를 지우는 방법(구글 계정의 앱 데이터 관리 화면)

기능이 선택형이라는 사실 자체도 방침에 쓰는 게 좋다. 필수인지 선택인지에 따라 심사에서 요구하는 고지 수준이 달라진다.

## 조립형 법적 문서

### 새 제품 추가는 태그 등록으로 끝난다

조항을 데이터로 두고 제품 태그로 조립하는 구조를 만들어 뒀더니, 새 제품의 방침·약관을 붙이는 비용이 몇 줄로 줄었다.

```ts
export type LegalProduct = 'keybloom' | 'metronome' | ... | 'openday';
export const legalProducts: LegalProduct[] = [..., 'openday'];
export const productNames = { ..., openday: { short: 'Openday', en: '...', ko: '...' } };
```

여기에 기존 조항의 `appliesTo`에 슬러그를 더하면 그 조항이 새 제품 페이지에도 붙는다. 오늘 붙인 광고 조항은 다른 웹앱이 쓰던 것을 태그만 추가해 재사용했다 — 같은 광고망이라 문구가 그대로 맞았다.

페이지 생성은 동적 라우트가 목록을 읽어 알아서 한다.

```ts
export function getStaticPaths() {
  return legalProducts.map((product) => ({ params: { product } }));
}
```

제품 목록에 하나를 넣으면 `/openday/privacy/`와 `/openday/terms/` 두 장이 자동으로 생긴다. 새로 쓴 조항은 제품 고유 사실(기록이 브라우저에만 남는다, 지우면 복구 불가) 두 개뿐이었다.

### 공통 조항은 새 기능 때문에 거짓이 된다

전에 배운 규칙은 "공통 조항에 특정 업체명·제품명을 넣지 말 것"이었다. 오늘 그 규칙이 이름에만 해당하는 게 아니라는 걸 알았다.

```text
기존: 기기를 떠나는 데이터는 광고와 분석이 전부입니다.
```

이 문장에는 고유명사가 없다. 그런데 한 제품에 클라우드 저장이 붙는 순간 사실이 아니게 된다. 공통 조항에 들어간 "무엇이 기기를 떠나는가" 같은 단정은 전 제품이 그 상태를 유지할 때만 참이다.

```text
수정: 기기를 떠나는 데이터는 아래에서 설명하는 제3자 서비스가 처리하는 것이 전부입니다.
```

구체적인 내용은 제품별 조항이 말하게 하고, 공통 조항은 "아래를 보라"로 넘긴다. 새 기능을 붙일 때 그 제품 조항만 보지 말고 공통 조항이 여전히 참인지 함께 확인하는 게 규칙이 됐다.

### 문단을 나누고 싶으면 같은 제목의 조항 두 개

조립기가 연속된 같은 섹션 제목을 한 번만 출력하도록 만들어 뒀다. 이 규칙 덕분에 한 조항을 여러 문단으로 늘리는 대신, 같은 섹션 제목을 가진 조항을 두 개 두면 결과가 한 덩어리로 보인다.

```ts
{ id: 'cloud-save-sandrop', section: { ko: '클라우드 저장' }, ... }
{ id: 'cloud-save-optout',  section: { ko: '클라우드 저장' }, ... }
```

문단마다 조항 id가 생기니 나중에 한 문단만 다른 제품에 붙이거나 지우기도 쉽다.

### 누수 검사는 매트릭스로

제품이 일곱이라 방침·약관 페이지가 열네 장이다. 조항 하나를 고치면 어느 페이지에 붙고 어느 페이지에는 안 붙는지를 눈으로 확인할 수 없다. 빌드 결과에서 문자열 포함 여부로 검사한다.

```js
// 있어야 할 문구
ck('로컬 저장 조항', /로컬 저장소\(localStorage\)에만 보관/.test(openday));
// 없어야 할 문구 — 다른 제품 조항이 새지 않았는지
for (const s of ['keybloom', 'sandrop', 'metronome'])
  ck(s, !/Openday|오픈데이/.test(read(s)));
```

"있어야 할 것"만 검사하면 절반이다. 조립형 문서에서 진짜 사고는 남의 제품 조항이 딸려 들어가는 쪽에서 난다. 페이지마다 있어야 할 문구와 없어야 할 문구를 같이 두는 게 핵심이다.

## 편집·재사용에서 겪은 것

### 소스에 여러 줄 문자열을 스크립트로 밀어 넣지 않는다

조항 본문을 스크립트로 파일에 써 넣었더니 문자열 안의 줄바꿈 표기가 실제 줄바꿈이 되어 리터럴이 중간에서 끊겼다. 빌드는 "문자열이 안 닫혔다"로 멈춘다.

```text
'첫 문단
두 번째 문단'   ← 따옴표 안에서 줄이 바뀌면 TS는 여기서 끊긴다
```

조항 본문은 한 줄 문자열로 유지하기로 했다. 문단이 필요하면 위에 적은 대로 조항을 나눈다. 소스 파일을 스크립트로 고칠 때는 이스케이프가 한 겹 더 있다는 걸 염두에 둔다.

### 두 번째 제품의 changelog는 파일 하나였다

업데이트 내역 표시를 처음 만들 때는 마크다운 파서, 버전·날짜 파싱, 한·영 분리, 접기 UI를 다 만들어야 했다. 오늘 다른 제품에 같은 걸 붙이면서 새로 만든 것은 버전 기록 마크다운 파일 하나뿐이다.

```astro
import changelogMd from '../data/sandrop-changelog.md?raw';
const changelog = parseChangelog(changelogMd, lang);
```

처음 만들 때 "이 제품 전용"으로 짜지 않고 마크다운을 인자로 받게 해 둔 값이 두 번째에서 돌아왔다.

## 배포 확인

### 반영 안 됐을 때는 본문으로 가른다

배포 직후 새 주소를 열면 홈 화면이 온다. 이 호스팅은 없는 경로에 상위 `index.html`을 정상 응답으로 돌려주기 때문에, 상태 코드만 보면 200이라 성공으로 읽힌다.

그래서 확인 기준은 상태 코드가 아니라 본문이다. 기대하는 문구가 나올 때까지 간격을 두고 몇 번 더 확인하면 배포 지연인지 진짜 실패인지 갈린다.

```bash
for i in 1 2 3; do
  curl -s "https://logstone.net/openday/privacy/?cb=$i" | grep -q "localStorage" && break
  sleep 25
done
```

같은 주소를 반복 조회할 때는 캐시를 우회할 파라미터를 붙인다. 이 구분을 안 하면 배포 지연을 실패로 읽는다 — 기다리면 되는 상황과 진짜 실패는 본문이 나올 때까지 확인해야 갈린다.
