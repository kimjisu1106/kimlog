## 게임 엔진과 규칙

### 기믹은 규칙(엔진)과 연출(UI)로 나눈다

"열쇠가 자물쇠에 닿을 때 잠금이 풀려야 한다" — 이 그림이 자연스러워서 엔진에서 잠금 해제 시점을 뒤로 미뤘다.

```dart
// ❌ 엔진 규칙을 바꿈 — 열쇠를 꺼내도 잠금을 안 풀고, 나중에 UI가 풀게
void _leaveBoard(Basket b) {
  b.revealed = true;
  // 잠금 해제를 여기서 뺐다
}
```

봇이 레벨을 못 풀었다. 이 게임은 500레벨을 봇으로 검증하는데, 봇이 열쇠를 꺼내도 잠금이 안 풀리니 뒤를 못 풀었다.

봇에겐 애니메이션이 없다. 열쇠를 꺼낸 그 순간 잠금이 풀려야 한다. "열쇠가 0.77초간 날아간다"는 사람이 보는 화면에만 존재한다.

```dart
// ✅ 규칙 — 열쇠가 보드를 떠나면 즉시 풀림 (봇·Python parity)
void _leaveBoard(Basket b) {
  b.revealed = true;
  if (b.keyFor != null) unlockedLocks.add(b.keyFor!);
}
```

```dart
// UI — 화면상 잠금만 열쇠 도착까지 지연
final Set<int> _visualLocked = {};
// 열쇠 비행이 잠긴 바스켓에 닿으면(t≥1) 시각 잠금 해제 + 팡
```

### 같은 교훈을 이틀 연속 밟았다

바로 어제 TIL에 "연출 지연은 UI에, 규칙은 엔진에"라고 써 놓고, 오늘 또 규칙 엔진에 지연을 넣었다가 봇이 막혔다.

머리로 아는 것과 손이 아는 것은 다르다. "열쇠가 도착할 때 열려야 한다"는 문장이 자연스러워서, 그걸 그대로 규칙으로 옮기고 싶은 유혹이 매번 생긴다. 어제 배운 걸 오늘 또 배웠다는 게 부끄럽지만, 이런 건 몇 번 밟아야 몸에 붙는 것 같다.

### 기존 판정에 조건 하나만 얹는다

기믹을 세 개 만들었는데(길막→자물쇠, 물음표, 얼음) 전부 같은 패턴이었다. 새 규칙을 통째로 짜지 않고, "선택 가능한가" 판정에 조건 한 줄만 얹는다.

```dart
List<int> selectablePositions() {
  ...
  if (isLocked(b)) continue;   // 잠긴 바스켓 — 열쇠 전엔 못 올림
  if (b.frozen) continue;      // 얼어 있으면 못 올림
  ...
}
```

이 한 줄만 넣으면 데드락 판정·`canLift`·봇이 전부 자동으로 따라온다. 그것들이 모두 `selectablePositions`를 기반으로 하기 때문이다. 판정의 단일 출처를 만들어 두면 기믹 추가가 싸진다.

### 몇 단계인지는 '있나 없나'가 아니라 값이 줄었는지로 잡는다

얼음이 이웃 3개가 나가야 3단계로 깨지게 만들었다. 처음엔 "얼음 칸 집합"에 드는지 빠지는지(집합 멤버십)로 깨짐을 감지했다.

```dart
// ❌ 집합 멤버십 — 완전히 깨질 때(집합에서 빠질 때)만 잡힌다
final nowFrozen = state.frozenBasketIndices();
if (_prevFrozen.length != nowFrozen.length) { ... }
```

이러면 3→2, 2→1 중간 단계는 여전히 집합에 있으니 안 잡혔다. 파편이 마지막에만 튀었다.

```dart
// ✅ 셀별 강도 값 — 줄어드는 순간마다 잡힌다
final nowIce = { for (i in frozen) i: board[i].iceStrength };
for (final e in _prevIce.entries) {
  if (nowIce[e.key] < e.value) {   // 강도가 줄었다
    spawnCrack(e.key, broke: nowIce[e.key] == 0);
  }
}
```

"있다/없다"가 아니라 "얼마나"를 추적해야 중간 단계가 보인다.

### undo 스냅샷에는 가변 상태를 전부 담는다

기믹마다 가변 상태가 늘었다 — 열린 자물쇠 집합, 바스켓별 얼음 강도. undo가 이걸 다 복원해야 한다.

```dart
_Snapshot _capture(...) => _Snapshot(
  ...,
  Set<int>.of(unlockedLocks),   // 열린 자물쇠
  // 바스켓별 iceStrength는 board 깊은 복사에 포함
);
```

기믹을 추가할 때마다 "이 상태가 undo로 되돌아가는가"를 확인하지 않으면, 되돌린 뒤 얼음이 안 얼어 있거나 잠금이 안 잠겨 있는 버그가 난다.

## 설계 판단

### 두 기능이 물리적으로 충돌하면 하나를 접는다

두 가지를 함께 넣으려 했다.

- crazy 레벨 = 한 기믹으로 판을 도배(70%)
- 얼음 = 이웃 3개가 나가야 깨짐

얼음으로 도배하면, 얼음 하나 깨려고 이웃 3개를 빼야 하는데 그 이웃들도 대부분 얼어 있다. 이웃을 깨려면 그 이웃의 이웃을 빼야 하고… 봇이 못 푼다. 실제로 얼음-crazy 판 4개가 전부 생성 실패했다.

둘 다 좋은데 함께는 성립하지 않았다. crazy는 물음표로만 도배하기로 했다. 물음표는 봇이 색을 아는 오라클이라 도배해도 항상 클리어 가능하기 때문이다.

기능을 다 욕심내 안 되는 걸 억지로 만들면 품질이 무너진다. 충돌을 인정하고 하나를 접는 게 낫다.

### 빈 칸을 막는 것보다 바스켓을 막는 게 항상 유효하다

처음 열쇠 기믹은 "길막" — 빈 칸을 벽처럼 막고 열쇠로 여는 것이었다. 문제는 생성기가 길막을 병목이 아닌 자리에 놓기 쉬웠다. 옆으로 돌아가면 되니 열쇠를 쓸 이유가 없는 판이 나왔다.

바스켓을 잠그는 방식으로 바꿨다. 바스켓은 그 자체로 통로를 막고(다른 바스켓이 못 지나감), 그림에도 필요하다(빈칸을 채워야 하므로). 그래서 잠긴 바스켓은 항상 의미가 있다 — 돌아갈 수도, 무시할 수도 없다.

막을 대상을 고를 때 "이게 안 막혀도 되는 경우가 있나"를 봐야 한다. 빈 칸은 우회 가능하고, 바스켓은 우회 불가능하다.

### 파편 — 단계별 세기 조절

같은 파편 시스템으로 중간 크랙과 마지막 팡을 세기만 다르게 냈다.

```dart
void _spawnIceShatter(int boardIndex, bool big) {
  final count = big ? 9 : 5;              // 팡은 조각 많이
  final vlo = big ? 2.2 : 1.2;            // 팡은 빠르게
  for (var n = 0; n < count; n++) {
    final a = (n / count) * 2 * math.pi + _rng.nextDouble();
    _iceShards.add(_IceShard(
      center + dir(a) * cell * 0.15,
      dir(a - 0.4) * cell * (vlo + rnd()),  // 살짝 위로 튀고
      ...));
  }
}
```

```dart
// 스텝 — 중력·페이드
for (final sh in _iceShards) {
  sh.pos += sh.vel * dt;
  sh.vel += Offset(0, 900 * dt);   // 중력
}
_iceShards.removeWhere((sh) => now - sh.born > 0.5);
```

파티클은 만드는 것보다 "언제 얼마나" 뿌릴지가 연출을 가른다. 세기 하나(`big`)로 크랙과 팡을 구분했다.

### 비행 속도는 감속 곡선과 함께 튜닝

열쇠 비행 속도를 여러 번 만졌다(0.55 → 0.8 → 1.15 → 1.3). 값 하나지만 easeInOut 감속이 걸려 있어, 같은 속도라도 도착할 때 부드럽게 멈춘다.

```dart
Offset get pos =>
    Offset.lerp(from, to, Curves.easeInOut.transform(t.clamp(0.0, 1.0)))!;
```

속도 튜닝은 숫자만 보고 정하기 어렵다. 기기에서 눈으로 몇 번 보고 맞췄다.

## Flutter UI

### 뒤로가기를 가로채 일시정지 띄우기

뒤로가기가 알림 없이 판을 버리고 나갔다. `PopScope`(뒤로가기 동작을 가로채는 위젯)로 잡아 톱니 메뉴와 같은 모달을 띄운다.

```dart
PopScope(
  canPop: false,   // 기본 뒤로가기 막고
  onPopInvokedWithResult: (didPop, _) {
    if (didPop) return;
    if (_gameOverStep != _GameOverStep.none) return;  // 모달 겹침 방지
    if (!_menuOpen) setState(() => _menuOpen = true);  // cog와 같은 메뉴
  },
  child: Scaffold(...),
)
```

어제도 겪은 건데 또 나왔다. 난이도 배지가 "매우 어려움"에서 "매우 어려"로 잘렸다. `Spacer`(빈 공간을 채워 미는 위젯, flex 1)와 `Flexible`(폭이 유동적인 위젯, flex 1)이 남은 폭을 반씩 나눠 가져서다.

## 프로세스

### 문자열 replace 앵커가 어긋나면 조용히 실패한다

코드를 스크립트로 수정하다가 "고쳤는데 왜 그대로지" 하는 일이 몇 번 있었다. 원인은 replace의 앵커 문구가 실제 코드와 미묘하게 달라 매칭이 안 된 것이었다. 특히 `dart format`이 코드를 재정렬하면 내가 기억하는 앵커와 실제가 달라진다.

```python
old = "..."
assert old in s, '앵커 없음'   # ← 이걸 넣으면 조용한 실패가 시끄러운 실패가 된다
s = s.replace(old, new, 1)
```

수정이 안 먹으면 "왜 안 되지"를 오래 붙들기 전에, 앵커가 실제로 파일에 있는지부터 확인해야 한다.

### 엔진 규칙을 바꾸면 생성 레벨을 재검증한다

얼음을 1단계에서 3단계로 바꿨더니, 기존에 생성해 둔 얼음 레벨들이 봇 클리어 불가가 됐다. 규칙이 바뀌면 봇의 행동이 바뀌고, 예전 규칙으로 "풀 수 있다" 판정받은 레벨이 새 규칙에선 못 풀 수 있다.

기믹 규칙을 건드릴 때마다 500레벨을 재생성했다. 생성 파이프라인이 각 레벨을 봇으로 재검증하므로, 못 푸는 레벨은 자동으로 걸러진다. 규칙과 콘텐츠가 따로 놀지 않게 하려면 규칙을 바꾼 뒤 콘텐츠를 다시 찍는 수밖에 없다.

## 요약

기믹 세 개를 만들며 반복해서 나온 건 "이건 규칙인가 연출인가"였다. 열쇠가 날아가는 것, 얼음이 쩍 갈라지는 것은 사람이 보는 연출이다. 열쇠를 꺼내면 길이 열리는 것, 이웃이 나가면 얼음이 약해지는 것은 규칙이다. 이 둘을 섞으면 봇이 막히거나 undo가 깨진다.

그리고 두 기능이 충돌할 때 — 3단계 얼음과 도배 — 억지로 둘 다 만들지 않고 하나를 접었다. 기능을 다 욕심내는 게 항상 좋은 건 아니다.
