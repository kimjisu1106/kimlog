## 스토어·정책 문서

### 데이터 보안 양식은 방침 본문을 읽는다

구글 플레이 데이터 보안 양식에 "이용자가 데이터 삭제를 요청할 수 있는 방편을 제공하나요"라는 항목이 있다. 여기에 예로 답하면 방침 URL을 함께 제출하는데, 심사는 그 페이지에서 삭제 방법이 실제로 적혀 있는지 본다.

- 방법이 페이지 어딘가에서 찾아지면 된다. 별도 페이지를 만들 필요는 없다
- 문장 속에 흘려 쓰기보다 번호 목록으로 나란히 두는 게 낫다. 사람이 훑든 심사자가 훑든 눈에 걸린다
- 삭제가 어디서 이루어지는지도 쓴다. "이용자 본인 계정에서 이루어지므로 앱과 무관하게 적용된다" 같은 한 줄이 양식의 취지에 맞는다

### 플랫폼 SDK가 방침 문구를 정한다

같은 회사의 저장 서비스를 써도 SDK에 따라 앱이 할 수 있는 일이 다르다. 한 게임은 플레이 게임즈 v2를 쓰는데 앱이 부를 수 있는 로그아웃이 없다. 앱 안에서 연결을 끊는 기능을 만들 수가 없으니 방침에 "앱에서 해제할 수 있다"고 쓰면 거짓이 된다.

- 그래서 그 앱 방침은 "앱 안에는 해제·삭제 기능이 없으며 계정 쪽에서 관리한다"가 됐다
- 웹 방식으로 붙인 다른 앱은 반대다. 브라우저가 직접 권한을 반납할 수 있어 "앱에서 연결 끊기"가 첫 번째 경로다

방침은 우리가 쓰고 싶은 문장이 아니라 코드가 할 수 있는 일을 적는 문서다.

### 조항을 복사하면 사실이 어긋난다

위 두 앱은 기능 이름이 같고(계정 연결로 진행 상황 저장) 저장 위치도 같은 회사 서비스다. 앞서 쓴 조항을 그대로 옮기면 빠르지만, 철회 방법 한 줄이 정반대가 된다.

전에 배운 규칙은 "공통 조항에 고유명사를 넣지 말 것"이었다. 여기서 배운 건 그 반대 방향이다. 제품별 조항이라도 다른 제품 것을 복사해 오면 같은 사고가 난다. 재사용의 단위는 문장이 아니라 사실관계다.

## 세션 협업 구조

### 상태 하나가 없어서 목록이 불어났다

여러 세션이 쓰는 우편함의 항목 상태가 대기·완료·반려 셋이었다. 전 세션에 알리는 공지도 대기로 올라오는데, 공지는 처리 주체가 없으니 모든 세션의 회신을 받기 전에는 닫을 수가 없다. 그래서 대기 목록이 계속 길어졌다.

상태를 하나 더 만들어 풀었다.

```text
open   누군가 처리해야 함
done   처리 완료
reject 반려
공지    읽고 반영하면 끝 — 회신 대기 없음
```

읽기만 하면 되는 일과 처리해야 하는 일이 같은 칸에 있으면, 처리 목록이 알림판을 겸하게 된다. 확답이 필요하면 공지와 별개로 그 세션 앞 대기 항목을 따로 만든다.

### 같은 브랜치를 공유하면 커밋을 세워둘 수 없다

푸시를 보류하기로 하고 커밋만 해 뒀는데 다음 확인 때 이미 올라가 있었다. 같은 저장소를 쓰는 다른 세션이 자기 커밋을 푸시하면서 앞선 커밋까지 함께 보낸 것이다. 브랜치가 하나이니 당연한 일이다.

- 확실히 붙잡아 두려면 커밋 자체를 미뤄야 하는데, 그러면 작업이 워킹 트리에 떠 있어 더 위험하다
- 그래서 규칙을 반대로 잡았다. 푸시 시점을 통제하려 하지 말고, 배포돼도 곤란하지 않은 상태에서만 커밋한다

### 채널의 도달 조건은 물리적 경계를 따른다

세션들이 한 컴퓨터에 있지 않다. 노트북 세션들은 같은 폴더를 공유해서 저장만 해도 서로 보이지만, 데스크톱 세션은 밀어 올려야 도착한다.

- 같은 폴더를 쓰는 쪽끼리는 파일을 통째로 새로 쓰면 상대 내용이 조용히 사라진다. 실제로 겪었다
- 다른 컴퓨터끼리는 그 사고가 안 난다. 대신 머지 충돌이 나고, 충돌은 눈에 보인다

"적었는데 왜 못 봤지"의 대부분은 경계를 잊은 것이다.

## 사라지지 않게 만들기

### 비인증 API는 IP당 시간당 60회다

한 제품의 업데이트 내역만 빌드할 때 깃허브 릴리스 API를 불러 만들고 있었다. 인증 없이 부르면 시간당 60회 제한이 걸리는데, 이 한도는 토큰이 아니라 IP 기준이다. 배포 서버는 IP를 여럿이 공유한다.

- 다시 말해 배포를 몇 번 했는지와 무관하게 막힐 수 있다
- 빌드 타임 페치는 "빌드가 도는 환경의 IP"가 한도의 주체라는 걸 계산에 넣어야 한다
- 토큰을 붙이면 한도가 5000회로 올라가지만, 토큰이 만료되면 같은 증상이 조용히 재발한다

### 조용한 실패가 문제를 오래 숨긴다

그 호출은 이렇게 감싸여 있었다.

```ts
try {
  const res = await fetch(url);
  if (res.ok) { /* changelog 생성 */ }
} catch {
  // 섹션 숨김 (에러 노출 금지)
}
```

실패하면 빈 배열이 남고, 렌더 쪽은 항목이 없으면 섹션을 통째로 감춘다. 그래서 화면에는 아무 흔적이 없다. 배포가 돌 때마다 운에 따라 있었다 없었다 했고, 언제부터 없었는지도 알 수 없었다.

- 실패를 숨기는 코드는 배포 뒤 알아채는 수단까지 같이 지운다
- 선택지는 셋이다. 실패를 눈에 보이게 하거나, 빌드를 세우거나, 실패할 자리를 없애거나

### 빌드 타임 페치를 번들로 바꾸기

세 번째를 택했다. 나머지 두 제품이 쓰던 방식이 이미 있었다.

```astro
import changelogMd from '../data/keybloom-changelog.md?raw';
const changelog = parseChangelog(changelogMd, lang);
```

전환에서 신경 쓴 것은 데이터 이관이다. API에 있던 릴리스를 그대로 가져와 같은 포맷으로 옮겨 담았다.

```bash
curl -s "https://api.github.com/repos/.../releases" -o rel.json
```

- 본문·날짜·언어 구분을 원본 그대로 유지해야 전환 전후 화면이 같다
- 자동 수집을 잃는 대신 통제를 얻는다. 무엇을 싣고 뺄지가 사람 손을 거친다
- 갱신 경로가 바뀌었다는 걸 그 제품 세션에 반드시 알려야 한다. 예전처럼 "재배포해 달라"고만 하면 이제 아무 일도 일어나지 않는다

## 확인 방법

### 배포 확인은 값이 아니라 구조로

재배포 뒤 페이지에서 버전 문자열을 찾아보고 반영됐다고 회신했다. 그런데 그때 섹션 자체가 빠져 있었고 문자열은 다른 자리에서 걸린 것이었다.

```bash
# 나쁨 — 값은 다른 자리에도 있을 수 있다
curl -s "$URL" | grep -q "0.1.6"
# 나음 — 있어야 할 구조를 본다
curl -s "$URL" | grep -q 'kb-changelog'
```

조항 검증에서는 "있어야 할 문구·없어야 할 문구"를 같이 보고 있었는데, 배포 확인에는 그 습관이 옮겨져 있지 않았다. 검증 기준은 한 곳에서만 엄격하면 소용이 없다.

### 캐시 때문에 "반영 안 됐다"는 보고가 온다

배포와 확인을 마치고 알렸는데 오 분 뒤 상대에게서 "아직 옛 내용이 보인다"는 회신이 왔다. 다시 받아 보니 우리 확인 결과와 같았다. 상대가 캐시를 본 것이다.

- 반영 확인을 요청할 때는 캐시 우회 방법까지 같이 알려 준다. 주소 뒤에 임의 파라미터를 붙이면 된다
- 반대로 우리가 확인할 때도 브라우저가 아니라 캐시 우회 요청으로 본문을 받아 판단한다

### 저장소 밖 설정은 문서에 박는다

스토어 콘솔의 개발자 연락처, 광고 인증 통과 여부, 검색 콘솔 제출 여부는 코드에서 확인할 방법이 없다. 확인할 수 없으니 세션이 바뀔 때마다 "이거 되어 있나요"를 다시 묻게 된다.

확인이 끝난 값은 프로젝트 문서에 확정 사실로 적는다. 날짜와 함께 적고, 재확인이 필요 없다는 것도 적는다. 사람에게 같은 질문을 반복하는 것도 비용이다.

## 편집 함정

### 도구를 거치면 이스케이프가 한 겹 더 풀린다

조항에 번호 목록을 넣으려고 줄바꿈 이스케이프를 문자열에 넣었다. 그런데 파일에는 실제 줄바꿈으로 들어갔고 문자열이 중간에서 끊겨 빌드가 멈췄다. 전에 같은 이유로 한 번 겪고 정리까지 해 뒀는데 재발했다.

원인은 층이 하나 더 있다는 것이다. 스크립트를 도구로 넘기는 과정에서 이스케이프가 한 번 풀리고, 스크립트 안에서 또 한 번 풀린다.

```python
NL = chr(92) + 'n'   # 중간 단계에서 풀릴 여지가 없다
body = '첫 줄' + NL + NL + '1. 항목'
```

- 규칙을 적어 두는 것만으로는 안 걸린다. 넣기 전에 실제 줄바꿈이 섞였는지 확인하는 절차가 있어야 한다
- 마크다운 목록은 이렇게 넣어도 렌더러가 번호 목록으로 그려 준다. 문제는 표현이 아니라 전달 경로다
