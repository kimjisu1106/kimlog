## 쌓아 두는 기록에서 값 뽑아내기

### "언제부터 세는가"를 마지막 이벤트로 잡으면 안 된다

이 앱은 상태를 직접 저장하지 않고 변동 기록만 쌓는다. 하트가 몇 개인지는 저장된 게 아니라 시작값에 변동을 전부 더해서 구한다. 지울 수도 고칠 수도 없으니 기록이 어긋날 일이 없다는 게 장점이다.

문제는 시간이 걸린 값이었다. 하트는 30분에 하나씩 차는데, 그 30분을 어디서부터 세느냐를 가장 최근 하트 기록의 시각으로 잡고 있었다.

```dart
// ❌ 하트에 관한 기록이면 무엇이든 기준이 된다
int _lastHeartTs() {
  var ts = 0;
  for (final d in _deltas) {
    if (d.kind == 'heart' && d.ts > ts) ts = d.ts;
  }
  return ts;
}
```

레벨에 들어가면 하나 빠지고, 아무것도 안 하고 나오면 하나 돌아온다. 둘 다 "하트에 관한 기록"이라 들락거릴 때마다 기준이 지금으로 밀렸다. 30분이 처음부터 다시 돌았다. 들어가기만 해도 그랬다.

원인은 두 가지를 한 값으로 다룬 것이다.

- 하트를 쓰고 받는 일
- 회복 시계가 도는 일

둘은 별개다. 시계는 가득 찬 상태에서 내려온 뒤로 계속 돌고, 그 사이에 무엇을 하든 박자가 안 바뀐다.

---

### 기준은 상태가 바뀐 지점이지 기록이 찍힌 지점이 아니다

고친 기준은 "가득 찬 상태에서 내려온 순간"이다. 이건 기록 하나만 봐서는 알 수 없다. 그 시점에 하트가 몇 개였는지를 알아야 하므로, 기록을 시간순으로 훑으면서 상태를 되짚어야 한다.

```dart
int _regenAnchor() {
  final events = _deltas.where((d) => d.kind == 'heart').toList()
    ..sort((a, b) => a.ts.compareTo(b.ts));
  var raw = startHearts;
  var anchor = 0;
  for (final d in events) {
    final before = raw.clamp(0, maxHearts);
    raw += d.value;
    final after = raw.clamp(0, maxHearts);
    if (before >= maxHearts && after < maxHearts) {
      anchor = d.ts;      // 여기서 시계가 시작된다
    } else if (after >= maxHearts) {
      anchor = 0;         // 다 찼으면 멈춘다
    }
  }
  return anchor;
}
```

두 가지를 조심했다.

시간순으로 정렬해야 한다. 회복분은 "기준 + 30분 × n" 같은 과거 시각으로 덧붙기 때문에, 기록이 추가된 순서와 실제 시각 순서가 다르다.

최댓값 비교는 상태를 구하는 식과 똑같이 해야 한다. 하트 개수를 구할 때 합계에 상한을 씌우므로, 되짚을 때도 매 단계 같은 방식으로 씌워야 중간에 어긋나지 않는다.

---

### 기준을 고정해도 중복 지급되지 않는다

기준이 안 움직이면 시간이 갈수록 "지난 주기 수"가 계속 커진다. 그대로 주면 과지급이다.

그런데 원래 코드가 이미 막고 있었다. 지난 주기 수를 그대로 주는 게 아니라 모자란 만큼으로 잘라서 준다.

```dart
final due = (now - anchor) ~/ regenMs;                 // 기준 이후 지난 주기
final add = due.clamp(0, maxHearts - current);          // 모자란 만큼만
```

기준을 앞당기는 일과 과지급을 막는 일은 원래 별개였는데, 예전 구조에서는 기준이 저절로 앞당겨져서 그 사실이 안 보였다. 자를 자리가 이미 있으니 기준은 고정해도 된다.

---

### 저장 형식을 안 바꾸면 지난 기록에도 소급된다

이번 수정은 저장 형식을 그대로 두고 읽는 방식만 바꿨다. 그래서 이미 쌓인 기록에도 새 규칙이 적용된다.

- 좋은 점: 옮기는 작업이 필요 없다. 앱을 새로 깔 필요도 없다
- 주의할 점: 예전 규칙으로 밀려 있던 값이 제자리를 찾으면서 한 번은 표시가 크게 달라져 보인다. 버그처럼 보이지만 정상이다

쌓아 두는 기록의 성질이기도 하다. 기록은 사실이고, 거기서 무엇을 읽어낼지는 나중에 바꿀 수 있다.

## 화면 생명주기

### 전체화면 광고는 앱을 뒤로 물린다

앞서 소리를 멈출 때 "앱이 완전히 가려진 경우"만 처리했다가, 최근 앱 목록에서는 그 신호가 안 와서 소리가 계속 나던 일이 있었다. 그때 판정을 앞에 있지 않으면 전부로 넓혔다.

며칠 뒤 확인해 보니 그 수정이 다른 문제까지 같이 해결해 놨다. 광고가 나오는 동안 배경음악이 겹쳐 나던 것이 멈춰 있었다.

전면·보상형은 둘 다 전체화면 광고라 광고 쪽이 자기 화면을 띄운다. 그러면 앱은 앞에서 물러난 것으로 잡힌다. "광고는 앱을 뒤로 안 보낸다"고 적어 뒀던 게 틀렸다 — 신호는 오고 있었고, 예전 판정이 좁아서 그 신호를 안 받았을 뿐이다.

계획대로 광고 쪽에 정지·재개를 따로 붙였다면 두 경로가 겹쳐 멈췄다 켜졌다 했을 것이다. 특히 보상형은 닫힘과 보상 지급 순서가 얽혀 있어 사고가 날 자리였다.

- 배너 광고는 다르다. 자기 화면을 안 띄우므로 생명주기가 안 바뀐다. 붙이게 되면 그때는 따로 처리해야 한다

### 할 일에 오래 남은 항목은 착수 전에 재현부터 확인한다

원인 설명까지 적어 둔 항목이라 당연히 남아 있는 줄 알았다. 실제로는 며칠 전에 이미 해결돼 있었고, 그걸 모른 채 고치러 들어갔으면 멀쩡한 걸 건드릴 뻔했다.

- 적어 둔 원인 설명이 그럴듯할수록 의심하기 어렵다
- 고치기 전에 지금도 그런지부터 본다. 특히 그 사이에 관련 있는 코드를 만졌다면 더

## 아이콘

### 작게 쓸 글리프는 선이 아니라 면으로 그린다

아이템 아이콘 셋 중 자석만 알아보기 어려웠다. 가는 선으로 U자를 그리고 극에 잔가지 네 개를 붙였는데, 실제로 쓰는 크기까지 줄면 잔가지 사이 여백이 선 두께보다 좁아져 한 덩어리로 뭉친다.

획이 의미를 나르는 아이콘(화살표)은 선이 맞다. 자석처럼 덩어리 자체가 형태인 것은 면으로 그려야 한다.

고리 모양은 도형을 빼지 않아도 만들 수 있다. 바깥 반원과 안쪽 반원을 반대 방향으로 이어 붙이면 채우기 규칙이 알아서 가운데를 비운다.

```dart
Path()
  ..moveTo((cx + rOut) * s, bodyTop * s)
  ..lineTo((cx + rOut) * s, cy * s)
  ..arcTo(outer, 0, math.pi, false)        // 오른쪽 → 아래 → 왼쪽
  ..lineTo((cx - rOut) * s, bodyTop * s)
  ..lineTo((cx - rIn) * s, bodyTop * s)
  ..lineTo((cx - rIn) * s, cy * s)
  ..arcTo(inner, math.pi, -math.pi, false) // 반대 방향으로 되돌아온다
  ..lineTo((cx + rIn) * s, bodyTop * s)
  ..close()
```

안쪽 호의 방향을 바깥과 같게 두면 구멍이 안 생기고 반원이 통째로 칠해진다. 두 번째 인자의 부호 하나가 그 차이다.

- 극은 몸통에서 살짝 띄운다. 붙이면 그냥 U자로 읽힌다
- 여러 크기로 한 번에 렌더해서 눈으로 본다. 큰 화면에서만 보면 뭉개지는 걸 못 본다

### 무료 아이콘도 조건을 보면 쓸 수 있다

널리 쓰는 무료 아이콘 묶음 중에는 출처를 밝히면 상업 앱에도 쓸 수 있는 것이 있다. "무료"와 "마음대로 써도 됨"이 같은 뜻은 아니지만, 조건이 출처 표기 하나뿐이면 실무에서는 충분히 쓸 만하다.

- 앱에 오픈소스 라이선스 화면이 이미 있으면 한 줄 추가로 끝난다
- 다만 표기 의무가 하나 늘면 그 목록을 계속 관리해야 한다. 직접 그릴 수 있는 단순한 모양이면 그리는 쪽이 가볍다
- 표기가 필요한 것과 직접 만든 것을 목록에서 섞지 않는다. 섞이면 무엇이 의무인지 흐려진다
