## 조립형 법적 문서

### 조항을 데이터로 쪼개고 태그로 조립한다

Privacy·Terms를 완성 문서로 관리하면 제품이 늘수록 합집합 문서가 된다 — KeyBloom 고객이 게임 재화 조항을 읽어야 하는 식. 조항 하나하나를 `{ id, appliesTo, section, body }` 데이터로 쪼개고, 페이지가 태그로 걸러 조립하게 바꿨다.

```ts
{ id: 'ads-adfit', appliesTo: ['keybloom', 'office-layout'],
  section: { en: 'Advertising', ko: '광고' },
  body: { en: '…', ko: '…' } }
```

통합본은 전 조항, 제품본은 `all` + 자기 태그 조항만. 공통 조항을 한 번 고치면 모든 페이지에 반영되고, 같은 섹션 제목이 연속되면 한 번만 출력해서 문서 모양을 지킨다.

### 페이지 N개는 동적 라우트 하나로

Astro의 파일명 대괄호 라우트(`pages/[product]/privacy.astro`)에 `getStaticPaths`로 제품 목록을 주면, 파일 하나가 `/keybloom/privacy/`부터 `/pawbit/privacy/`까지 전부 만든다. 제품 추가 = 데이터에 슬러그 등록이 전부고, 페이지 파일은 늘지 않는다.

```ts
export function getStaticPaths() {
  return legalProducts.map((product) => ({ params: { product } }));
}
```

### 조립형 문서의 함정 — 공통 조항에 고유명사 금지

공통(all) 조항에 "Creem·카카오·Google이 보유한 데이터는…"처럼 업체를 열거했더니, 결제가 없는 제품의 페이지에도 Creem이 새어 나왔다. 공통 조항은 "위에 설명된 제3자 서비스"처럼 일반화해야 어떤 조합에서도 정확하다. 사람 눈으로는 놓치기 쉬워서, 페이지마다 "반드시 있어야 할 문자열 / 있으면 안 되는 문자열"을 대조하는 검증 스크립트를 빌드 뒤에 돌려 잡았다 — 조립형 문서에는 이 자동 대조가 사실상 필수다.

## 릴리스 노트와 Changelog

### GitHub 릴리스 목록을 빌드 타임에 읽어 정적 Changelog로

업데이터용 파일(latest.json)에는 최신 한 버전만 있어서 전체 이력은 Releases API(`api.github.com/repos/…/releases`)를 쓴다. 정적 사이트라 빌드 시점에 한 번 fetch해 HTML로 구우면 런타임 호출도, 요청 한도 걱정도 없다. draft·prerelease는 걸러내고, 릴리스가 없거나 fetch가 실패하면 섹션 자체를 렌더하지 않는다 — 에러 화면을 고객에게 보여줄 이유가 없다.

### 한 릴리스 노트에 두 언어 — 구분선 규약

릴리스 body를 언어별로 따로 쓰는 대신, 한 body에 한국어 → `---` 한 줄 → 영어로 적는 규약을 정했다. 소비하는 쪽에서 구분선으로 갈라 로케일에 맞는 절반만 보여준다. 구분선이 없으면 통짜로 취급해 어느 쪽에서도 깨지지 않는다. 발행 규약과 소비 코드가 한 쌍인 계약이라, 릴리스 절차 문서에 같이 적어야 유지된다.

### 접기는 details, 더보기는 hidden

접이식 UI는 `<details><summary>`가 JS 없이 해결한다. "최신 3개만 보이고 더보기" 는 4번째부터 `hidden` 속성을 주고 버튼 클릭에 속성만 제거 — 상태 관리랄 게 없는 가장 싼 구현.

### 마크다운 렌더는 신뢰 소스에서만

릴리스 노트는 `marked`(마크다운을 HTML로 바꿔 주는 라이브러리)로 HTML로 바꿔 `set:html`로 꽂는다. marked는 입력을 소독(sanitize)하지 않으므로, 이렇게 꽂아도 되는 건 내가 쓰는 릴리스 노트처럼 출처를 통제하는 콘텐츠뿐이다. 외부인이 쓸 수 있는 입력이면 소독 단계가 따로 필요하다.

## 멀티 세션 협업

### 저장소를 세션 간 우편함으로

프로젝트마다 담당 AI 세션이 따로 돌면 조율이 전부 사용자를 거치게 된다. 공유 저장소에 요청함 파일(INBOX.md)을 두고 규약을 정하면 세션들끼리 비동기로 협업한다 — 다른 세션은 요청을 적고 push, 허브 세션은 세션 시작 시 open 항목을 처리하고 done/rejected로 회신. 모든 왕래가 git 이력으로 남아 추적도 된다. 각 세션이 "시작 시 요청함 확인" 룰을 자기 문서에 박으면 사람 알림 없이 자율로 돈다.

### 같은 폴더를 공유하는 세션들의 편집 충돌

여러 세션이 한 로컬 폴더에서 일하면 커밋이 서로를 쓸어 담는다 — 내 미커밋 수정이 남의 커밋에 실려 가고, 응답 줄이 다른 세션 커밋에 묻혀 사라지기도 했다. 공유 파일은 고치기 전 `git pull`, 고친 뒤 즉시 commit & push가 규칙이다. 사이가 벌어질수록 충돌 확률이 커진다.

## 스토어 운영

### 정책 URL은 제품별로 — 심사 대조가 1:1이 된다

여러 앱이 정책 URL 하나를 나눠 쓰면 심사관이 문서에서 그 앱 얘기를 찾아야 하고, 무관한 조항(다른 앱의 광고·결제)이 오해를 부른다. 제품별 정책 페이지를 스토어에 제출하면 Play의 데이터 보안 양식과 문서가 1:1로 대조되고, 조항이 바뀔 때 어느 앱의 양식을 고쳐야 하는지도 명확해진다. 대신 "조항 변경 시 해당 앱 양식 동기화"라는 연동 관리가 새로 생긴다 — 이것도 계약으로 문서화해야 한다.
