한 기기에서 업데이트만 했는데 plus 라이선스가 풀리고 활성화 슬롯이 깎이던 버그를 잡으며 나온 것들.

## 버그를 좁히기

### 무엇이 남고 무엇이 사라졌나로 원인 범위를 좁힌다

라이선스는 브라우저 저장소(localStorage)에 있다. "업데이트가 저장을 통째로 날렸다"가 맞다면, 같은 저장소에 있는 언어·튜토리얼 봤는지 같은 값도 같이 초기화돼야 한다.

확인해 보니 언어·튜토리얼은 멀쩡했고 라이선스만 사라졌다. 그러면 원인은 "저장 소실"이 아니라 "특정 코드가 라이선스만 지운 것"으로 좁혀진다. 같은 그릇에 담긴 것 중 일부만 사라졌다면, 그릇이 깨진 게 아니라 누군가 그것만 골라 버린 것이다.

- 교훈: 무엇이 사라졌는지뿐 아니라 무엇이 남았는지를 같이 보면, 같은 계층(저장소)의 문제인지 특정 로직의 문제인지 단번에 갈린다.

## 권한을 지우는 코드

### 되돌릴 수 없는 삭제는 애매한 응답에 하지 않는다

실행 때 도는 라이선스 재검증이 이렇게 돼 있었다.

```ts
// ❌ "active"가 아니면 무조건 삭제 — 서버 딸꾹질·에러 응답에도 권한이 날아간다
if (data.status === "active") keep();
else clearLicense();
```

서버가 잠깐 이상하게 답하거나(429·500) 상태가 불명확하기만 해도 라이선스가 통째로 지워진다. 유료 사용자가 서버 사정으로 풀려서는 안 된다.

```ts
// ✅ 정상 응답 + 명시적 취소·만료일 때만 삭제, 나머지는 유예로 버틴다
if (res.ok && data.status === "active") keep();
else if (res.ok && REVOKED.has(data.status)) clearLicense();
else { /* 비-2xx·오류·상태 불명 — 삭제 안 함. 유예 안이면 유지, 넘으면 잠그되 저장은 남김 */ }
```

- 교훈: 되돌릴 수 없는 조치(삭제·차단)는 "확실한 부정"에만 건다. 애매하면 아무것도 지우지 말고 유예로 버티게 한다 — 실패는 안전한 쪽(권한 유지)으로 기울여야 한다.

### fetch는 HTTP 에러에 throw하지 않는다 — res.ok 확인

위 버그의 한 축은 `res.ok`을 안 본 것이다. `fetch`는 네트워크가 끊길 때만 throw하고, 4xx·5xx는 정상적으로 응답 객체를 돌려준다.

```ts
const res = await fetch(url);   // 500이어도 여기서 안 터진다
const data = await res.json();  // 에러 바디도 파싱됨
if (data.status === "active") {...}  // res.ok을 안 보면 에러 응답을 "정상 아님"으로 오판
```

- 교훈: `fetch` 뒤엔 `res.ok`(또는 status)를 먼저 확인한다. 안 그러면 서버 에러 바디가 정상 로직에 섞여 든다.

## 라이선스 모델

### 로컬 UUID 활성화의 함정 — 저장이 사라지면 슬롯이 샌다

이 앱은 활성화 때 로컬에 UUID(instance_id)를 만들어 결제사에 등록하고, 그걸로 기기 수를 센다(하드웨어 지문이 아니다). 로컬 저장이 사라지면 앱은 활성화를 잊고, 다시 활성화하면 새 UUID가 새 기기로 등록돼 슬롯이 하나 더 소비된다. 옛 등록은 유령으로 남아 슬롯을 계속 차지한다.

그래서 이 모델에선 로컬 저장(instance_id)을 함부로 지우지 않는 게 핵심이다. 지우는 순간 재활성화가 강제되고, 재활성화는 곧 슬롯 누수다.

- 교훈: 식별자를 로컬에만 두는 활성화 방식은 "저장을 지운다 = 슬롯을 하나 버린다"와 같다. 로컬 삭제 경로를 최소화하고, 지워야 할 땐 서버 슬롯도 함께 반납(deactivate)해야 새지 않는다.

## 요약

- 무엇이 남고 사라졌나를 같이 보면 저장 문제인지 로직 문제인지 갈린다
- 되돌릴 수 없는 삭제는 "확실한 부정"에만, 애매하면 유예로 유지(fail-safe)
- `fetch`는 HTTP 에러에 안 터진다 → `res.ok` 먼저 확인
- 로컬 UUID 활성화는 저장을 지우면 재활성화로 슬롯이 샌다 → 로컬 삭제를 아낀다
