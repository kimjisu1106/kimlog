## 정적 사이트 운영

### 페이지를 지우지 않고 "잠시 닫기"

출시가 밀려 소개 페이지를 잠깐 내려야 할 때, 파일을 지우면 되살릴 때 다시 만들어야 하고 문구·자산도 함께 사라질 위험이 있다. 닫는 일을 두 층으로 나눠 두면 안전하다.

- 목록 노출 — 제품 데이터에 `hidden` 필드를 두고 홈 카드가 그 값을 본다. 페이지는 살아 있고 링크만 사라진다.
- 페이지 자체 — 정적 사이트는 파일이 곧 주소라 "조건부로 안 만들기"가 안 된다. 그래서 내용 컴포넌트는 그대로 두고 얇은 래퍼 파일만 내린다.

```ts
// products.ts — 스위치 하나로 목록에서 뺀다
{ slug: 'sandrop', hidden: true, /* … */ }
```

내용·자산·문구가 전부 남아 있으니 복구는 래퍼 다섯 줄을 되돌리는 것으로 끝난다. 대신 복구 절차를 문서에 적어 두는 것까지가 한 세트다 — 몇 주 뒤의 나는 무엇을 지웠는지 기억하지 못한다.

### 같은 경로 아래에도 계약 URL과 홍보물이 섞여 있다

`/sandrop/` 아래에 소개 페이지와 방침·약관이 함께 있었다. 무심코 폴더째 지우면 앱에 내장되고 스토어에 제출된 방침 주소까지 죽는다. 페이지를 내리기 전에 갈라야 할 질문은 하나다 — 이 주소가 어딘가에 박혀 있는가.

- 박혀 있는 것(계약) — 앱 안 링크, 스토어 등록 정보, 결제사에 제출한 주소. 바꾸려면 상대의 재배포가 따라온다.
- 박혀 있지 않은 것(홍보물) — 소개 페이지, 목록 카드. 언제 내려도 아무도 깨지지 않는다.

지우고 나서 빌드 결과에 계약 주소가 남아 있는지 직접 확인하는 것도 습관으로 둘 만하다.

## 빌드 타임 데이터

### 비공개 저장소의 changelog — API 대신 번들

공개 저장소는 릴리스 목록을 API로 가져오면 되지만, 비공개는 무인증 요청이 404다. 토큰을 붙이는 건 정적 사이트에 과하다. 그래서 내역을 적은 마크다운을 소비자 쪽 저장소에 두고 빌드할 때 읽었다.

```ts
import md from '../data/metronome-changelog.md?raw';
const entries = parseChangelog(md, lang);
```

`?raw`는 파일을 문자열 그대로 가져오는 임포트라 파일 시스템 접근이 필요 없고, 빌드 환경이 어디든 똑같이 동작한다. 대신 갱신이 사람 손을 타므로 "누가 언제 고치는가"를 규약으로 정해 두어야 한다 — 여기서는 앱 세션이 요청을 보내면 샵이 그 파일만 고친다.

### 같은 날짜 항목의 순서는 정렬이 지켜 준다

날짜 내림차순으로 정렬하는데 1.16과 1.17이 같은 날이었다. 비교값이 같으면 자바스크립트의 정렬은 원래 순서를 그대로 둔다(안정 정렬이 표준으로 보장된다). 그래서 파일에 최신을 위에 써 두면 그 순서가 화면에도 그대로 나온다.

```ts
.sort((a, b) => b.date.localeCompare(a.date)) // 같은 날짜면 파일 순서 유지
```

날짜만으로 못 가르는 항목이 생길 때 억지로 시간까지 넣지 않아도 되는 이유다.

## CSS 함정

### 축약형이 개별 속성을 통째로 덮는다

히어로에 상단 여백을 줬는데 화면에서는 붙어 있었다. 원인은 공용 컨테이너의 축약형이었다.

```css
.kb-wrap { padding: 0 20px; }        /* 상하 여백을 0으로 함께 지정한 셈 */
.mt-hero-inner { padding-top: 72px; } /* 명시도가 같으면 순서 싸움 */
```

축약형(`padding`)은 네 방향을 전부 쓰기 때문에, 뒤에 오면 개별 속성(`padding-top`)을 지운다. 같은 요소에 두 클래스를 함께 쓰면 승부는 명시도가 같을 때 파일 순서로 갈리는데, 번들러가 순서를 바꾸면 결과도 바뀐다. 순서에 기대지 않으려면 명시도를 올린다.

```css
.kb-wrap.mt-hero-inner { padding: 80px 20px 88px; }
```

교훈은 둘이다 — 공용 컨테이너에는 축약형을 쓰지 말고 필요한 방향만 지정할 것, 그리고 "내 스타일이 무시된다"는 증상에서 명시도만 보지 말고 축약형을 의심할 것.

### gap으로 그린 구분선은 빈칸에서 정체를 드러낸다

칸 사이에 선을 그리려고 그리드에 배경색을 깔고 `gap: 2px`으로 셀 사이만 비추는 기법을 썼다. 칸이 딱 맞으면 선처럼 보이지만, 카드가 다섯 개인데 3열이면 마지막 칸이 통째로 비면서 배경색이 넓게 드러난다.

```css
.mt-grid { display: grid; grid-template-columns: repeat(3, 1fr);
           gap: 2px; background: rgba(32,30,29,.4); }
.mt-feature { background: var(--bg); }  /* 셀이 배경을 가려서 선만 남는다 */
```

해결은 배경색으로 채운 빈 셀 하나를 더 두는 것이다. 항목 수가 열 수의 배수가 아닐 때 생기는 문제라, 이 기법을 쓸 거면 필러를 처음부터 계산에 넣는 편이 낫다.

## 검증과 협업

### 자동 검증이 자기 스크립트를 세고 있었다

"항목이 셋뿐이니 더보기 버튼은 없어야 한다"를 확인하려고 빌드 결과에서 문자열을 셌는데 실패로 나왔다. 버튼은 실제로 없었고, 페이지에 함께 실린 스크립트의 `getElementById('kb-cl-more')` 안 문자열이 걸린 것이었다.

```js
h.includes('kb-cl-more')              // 스크립트 속 이름까지 잡힘
/<button class="kb-cl-more"/.test(h)  // 실제 요소만
```

문자열 검사로 렌더 결과를 확인할 때는 태그 형태까지 넣어 좁히는 게 맞다. 검증이 틀렸는데 코드를 고치러 가는 게 더 위험하니, 실패가 나오면 검사부터 의심해 볼 일이다.

### 제품 문구의 원본은 하나여야 한다

제품 페이지 문구는 스토어 등록 정보에서 가져왔는데, 원본이 갱신된 걸 모르고 옛 판을 그대로 두고 있었다. 앱 쪽에서 알려 준 뒤에야 알아챘다.

문구처럼 여러 곳에 복제되는 정보는 어디가 원본인지 정하고, 원본이 바뀌면 통보하는 규약을 함께 둬야 한다. 이번 건에서 배운 것 하나 더 — 사실이 바뀌는 문장(연결 없이도 된다 같은 서술)은 복제본에서 특히 위험하다. 기능이 조금 달라지면 광고가 곧 거짓이 되기 때문에, 애매하면 그런 문장은 아예 싣지 않는 편이 낫다.
