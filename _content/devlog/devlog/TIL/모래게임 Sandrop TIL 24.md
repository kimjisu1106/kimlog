## 측정으로 난이도를 정할 때

### 한 숫자에 두 성질이 섞여 있으면 갈라서 잰다

이 게임은 판의 난이도를 봇으로 잰다. 봇이 한 수마다 정해진 확률로 실수하고, 여러 번 돌려 성공 비율을 낸다.

그런데 최고 난이도로 만든 판이 사람에게는 한 번에 풀렸다. 수치는 목표 안이었다.

그 비율에는 두 가지가 섞여 있었다. 계획이 어려워서 못 깨는 것과, 한 번 삐끗하면 끝이라 못 깨는 것이다. 사람이 어렵다고 느끼는 건 앞의 것뿐이다.

섞인 것을 갈라내는 방법은 단순했다. 섞이게 만든 값을 인자로 빼고 여러 번 재는 것이다.

```python
g0  = _random_clear_rate(d, runs, level_id, mistake=0.0)
g10 = _random_clear_rate(d, runs, level_id, mistake=0.10)
g20 = _random_clear_rate(d, runs, level_id, mistake=0.20)
```

실수 0퍼센트는 계획 난이도, 20퍼센트는 실수에 얼마나 가혹한가다. 문제의 판은 0퍼센트에서 절반이 깨졌다. 계획은 쉬운데 실수에만 가혹한 판이라는 게 두 숫자를 나란히 놓자 바로 보였다.

- 지표가 이상하면 더 정교한 지표를 찾기 전에, 지금 지표에 무엇이 섞여 있는지부터 본다
- 섞인 성질은 대개 이미 코드 안에 상수로 박혀 있다. 그걸 인자로 빼는 것이 첫 수다

---

### 비교하는 두 숫자가 같은 대상에서 나왔는지 본다

새로 넣은 세 값이 앞뒤가 안 맞았다. 실수를 더 하는 쪽이 더 잘 깨는 것으로 나왔다.

원인은 잰 대상이 달랐다는 것이다. 기존 값은 속도 때문에 절반 해상도로 줄인 판에서 쟀고, 새 값은 실제 판에서 쟀다. 서로 다른 판의 성적을 나란히 놓고 비교하고 있었다.

고치면서 알게 된 게 더 컸다. 지금까지 화면에 뜨던 난이도가 전부 축소판 기준이었고, 축소판은 더 쉽게 나온다. 즉 표시되던 난이도가 실제보다 낮게 잡혀 있었다.

- 값이 앞뒤가 안 맞으면 계산식보다 입력을 먼저 의심한다
- 속도 때문에 둔 근사치는 근사치라는 표시가 안 붙는다. 어디서 쓰이는지 세어 두지 않으면 어느새 정식 값처럼 쓰인다

---

### 무작위가 없어도 결과는 흔들릴 수 있다

실수 확률이 높은 봇이 더 잘 깨는 레벨이 47개 나왔다. 함정이 있는 판이면 실제로 그럴 수 있어서 진짜인지 봐야 했다.

표본 8개를 40회씩 다시 재보니 6개가 사라졌다. 8회로는 값이 0.12와 0.35 사이에서 흔들렸다.

실수가 0이면 결정적일 거라 생각한 게 틀렸다. 점수가 같은 수가 여럿일 때 무엇을 고르느냐가 갈림길마다 쌓여, 실수를 안 해도 결과가 갈린다.

- 반복 횟수를 정하기 전에, 같은 입력으로 여러 번 돌려 값이 얼마나 흔들리는지부터 본다
- "무작위 요소를 껐으니 결정적"은 확인해야 하는 가정이지 전제가 아니다

## 규칙을 고칠 때

### 상한을 없애면 그 상한이 막고 있던 것이 나온다

얼음이 녹는 조건에 상한 3이 걸려 있었다. 그래서 옆에 아직 못 나간 이웃이 넷일 때 셋만 나가도 녹았다.

```dart
b.iceStrength = neighbors < 1 ? 1 : neighbors;   // 상한 3 제거
```

이걸 없애자 새 문제가 생겼다. 얼음 둘이 붙어 있으면 서로가 서로의 이웃인데 둘 다 못 나가므로, 어느 쪽도 조건을 못 채운다. 영영 안 풀리는 판이 됐다.

상한이 우연히 이 교착을 막고 있었던 것이다.

- 해결은 규칙이 아니라 배치에서 했다. 얼음끼리 이웃하지 않게 두면 규칙은 단순하게 남는다
- 제약을 걷어낼 때는 그 제약이 부수적으로 막고 있던 게 있는지 본다. 대개 문서에 안 적혀 있다

---

### 예외 경로는 한 번 고쳐도 또 샌다

이 생성기에는 정상 경로가 실패하면 떨어지는 안전망이 있다. 하루 전에 여기로 벽이 안 넘어가는 걸 고쳤는데, 다음 날 같은 자리에서 기믹 세 종류가 통째로 빠지는 걸 또 발견했다.

```python
# 어제 고친 것 — 벽만 넘겼다
d = build(..., walls=fb_walls)

# 오늘 — 정상 경로가 넘기는 것을 전부 넘긴다
d = build(..., walls=fb_walls, **_fb_gimmicks(cells, rng))
```

예외 경로가 사각지대라는 건 이미 알고 있었는데도, 고칠 때 눈에 보이는 인자 하나만 채우고 끝냈다.

- 예외 경로를 고칠 때는 정상 경로가 넘기는 인자 목록을 옆에 놓고 하나씩 대조한다
- 한 번 샌 자리는 다시 샌다. 같은 자리를 두 번째 고칠 때는 전수로 본다

---

### 규칙 엔진이 두 곳에 있으면 같이 고친다

이 프로젝트는 게임 규칙이 앱(Dart)과 레벨 생성기(Python) 양쪽에 있다. 생성기가 판을 만들 때 풀리는지 검증해야 해서다.

그래서 규칙을 하나 고치면 두 곳을 고쳐야 하고, 안 그러면 생성기는 풀린다고 하는데 앱에서는 안 풀리는 판이 나온다.

```python
b.ice_strength = max(1, neighbors)   # Dart 쪽과 같은 식
```

- 두 구현이 어긋나지 않는지는 사람이 기억할 게 아니라 테스트가 볼 일이다. 이 프로젝트는 생성된 레벨 전체를 봇이 실제로 깨보는 테스트가 있어서 어긋나면 거기서 걸린다

## 안드로이드 전체화면 광고

### 몰입 모드에서는 광고가 자기 UI를 화면 밖에 그린다

전면 광고에 닫기 X가 안 떠서 광고를 닫을 수 없었다.

앱이 시스템 바를 숨기는 몰입 모드로 돌고 있어서, 광고가 안전영역을 0으로 보고 자기 UI를 화면 밖에 배치한 것이다. 타깃 API 35 이상에서 알려진 문제다.

```dart
await ad.setImmersiveMode(true);   // 광고에 몰입 모드임을 알린다
await ad.show();
```

- 전체화면을 쓰는 앱은 남의 전체화면 UI와 부딪힌다. 광고·결제·공유처럼 남이 그리는 화면이 있으면 거기서 확인한다

---

### 같은 원인이어도 해법은 종류마다 다를 수 있다

위 방법으로 전면 광고는 고쳐졌는데 보상형은 안 됐다. 보상형은 X만이 아니라 타이머와 보상 안내까지 통째로 안 그려졌다.

보상형은 광고가 떠 있는 동안만 시스템 바를 되돌리고, 닫히면 원래대로 돌리는 식으로 고쳤다.

```dart
await SystemChrome.setEnabledSystemUIMode(SystemUiMode.edgeToEdge);
await ad.show(onUserEarnedReward: (_, _) => onReward());
// 닫힘·실패 콜백 양쪽에서 immersiveSticky로 복귀
```

- 한쪽이 고쳐졌다고 다른 쪽이 고쳐진 게 아니다. 종류가 나뉜 기능은 종류마다 확인한다
- 되돌리는 처리는 성공 경로만이 아니라 실패 경로에도 넣어야 한다. 광고가 뜨다 실패하면 시스템 바가 켜진 채로 남는다

---

### 로그에 보이는 오류가 원인이라는 보장은 없다

닫기 버튼을 찾는 동안 로그에 자바스크립트 오류가 찍혀 있었고, SDK가 네 개 메이저나 뒤처져 있었다. 그래서 그것부터 올렸다.

안 고쳐졌다. 오류는 계속 났고 버튼은 여전히 없었다. 원인은 위에 적은 몰입 모드였다.

SDK를 올린 것 자체는 필요한 일이었지만, 이 문제의 원인이라고 단정한 것은 오진이었다.

- 눈에 띄는 오류와 지금 겪는 증상이 이어지는지 먼저 확인한다. 큰 라이브러리는 무해한 오류를 늘 찍는다
- 고치기 전에 "이게 원인이면 왜 이 증상이 나오는가"를 한 문장으로 말할 수 있어야 한다

## 그림을 파일로 받을 때

### 벡터를 이미지로 구우면 색이 늘어난다

5색으로 그렸다는 그림을 게임에 넣었더니 딸기가 갈색이 되고 초가 사라졌다.

파일을 열어보니 색이 39~59개였다. 벡터를 PNG로 구울 때 경계를 부드럽게 깎는 옵션이 기본으로 켜져 있어, 순색 사이에 중간값이 깔린 것이다.

이 게임은 그림의 색 하나가 곧 모래 색 하나여서 최대 6색으로 줄인다. 그 과정에서 경계마다 낀 중간값까지 한 덩어리로 묶이니 평균이 엉뚱한 색으로 나왔다.

- 그림을 데이터로 쓰는 파이프라인에서는 "보기 좋게" 하는 옵션이 손해다. 내보낼 때 안티에일리어싱을 끈다
- 이런 건 에러가 안 난다. 그냥 뭉갠 결과가 조용히 등록된다

---

### 리샘플 흔적은 색 히스토그램으로 판별한다

그림이 문제인지 변환이 문제인지 가리려면 파일을 재보면 된다. 두 가지를 봤다.

```python
# 1. 여분 색이 순색 두 개의 정확한 중간값인가
for t in (0.25, 0.5, 0.75):
    mid = tuple(a[k] + (b[k] - a[k]) * t for k in range(3))

# 2. 반투명 픽셀이 있는가 — 한 칸씩 그렸다면 0이어야 한다
semi = sum(1 for p in pixels if 0 < p[3] <= 200)
```

여분 색의 16퍼센트가 정확한 중간값이었고 반투명 픽셀이 100개 넘게 있었다. 둘 다면 리샘플(크기를 바꾸며 픽셀을 다시 계산하는 것)이나 안티에일리어싱을 거쳤다는 뜻이다.

- 중간값을 지우는 후처리도 가능하지만 복원이 아니라 추정이다. 원본이 벡터면 설정만 바꿔 다시 받는 쪽이 정확하다

---

### 재보기 전에 원인을 말하지 않는다

이 문제의 원인을 세 번 잘못 짚었다.

| 짚은 것 | 왜 틀렸나 |
| --- | --- |
| 색이 39~59개나 돼서 | 94색짜리 그림도 멀쩡하게 나왔다 |
| 강조색 면적이 작아서 | 딸기는 전체의 7.6퍼센트로 작지 않았다 |
| 32칸으로 그려 확대해서 | 잘 나온 기존 그림도 같은 패턴이었다 |

셋 다 그럴듯했고 셋 다 파일을 재기 전에 말한 것이다. 진짜 원인은 히스토그램(값이 얼마나 분포하는지 센 표)을 뽑고서야 나왔다.

- 원인을 말할 수 있는 시점은 그 원인을 구별하는 측정을 한 뒤다
- 반례가 될 만한 케이스를 먼저 찾아본다. "색이 많아서"라면 색이 더 많은데 멀쩡한 것이 있는지 보면 30초에 끝난다

## Flutter 화면

### 한 덩어리로 보이면 탭도 한 덩어리여야 한다

레벨 목록에서 그림·번호·난이도가 한 줄로 붙어 있는데, 그림에만 탭이 걸려 있었다. 라벨에도 걸어 줬더니 이번엔 둘 사이 여백이 죽은 자리로 남았다.

`HitTestBehavior.opaque`를 주면 자식이 그리지 않은 빈 공간까지 그 영역으로 친다.

```dart
GestureDetector(
  onTap: onTap,
  behavior: HitTestBehavior.opaque,   // 빈 공간까지 이 줄의 것으로
  child: Row(children: [thumb, label]),
)
```

- 세로 패딩은 감싸는 범위 밖에 뒀다. 줄 사이 간격까지 먹으면 위아래 항목이 잘못 눌린다

---

### 자식에 같은 탭을 또 걸면 반응이 갈린다

위처럼 부모가 받게 한 뒤에는 자식 쪽 `GestureDetector`를 지워야 한다. 남겨 두면 그 자리만 자식이 먼저 가져가서, 눌리는 자리마다 반응이 미묘하게 달라진다.

예외는 안에 든 진짜 버튼이다. 자기 탭을 가진 버튼은 그대로 두면 안쪽이 이긴다.

- 겹친 제스처는 안쪽이 이긴다. 이걸 알면 "전체를 누르게 하되 버튼만 따로"가 추가 코드 없이 된다

---

### 적용된 값과 설정한 값은 다르다

언어 설정이 한국어·영어·시스템 따름 세 가지다. 방침 페이지를 열 때 한국어면 국문 위치로 보내려고 했는데, 설정값을 보면 "시스템 따름"일 때 어느 쪽인지 알 수 없다.

```dart
// ❌ 설정값 — system이면 판정 불가
if (_lang == AppLang.ko) ...

// ✅ 적용된 결과
bool get isKorean => t is StringsKo;
```

- 사용자가 고른 값과 실제로 적용된 값이 다를 수 있는 설정은 "따름" 선택지가 있는 것 전부다. 테마·언어·알림이 대개 그렇다

---

### 외부 링크는 브라우저에 넘긴다

앱 안에서 방침·약관을 보여줄 때 화면을 만들지 않고 기본 브라우저로 넘겼다.

```dart
final target = isKorean ? '$url#ko' : url;
launchUrl(Uri.parse(target), mode: LaunchMode.externalApplication);
```

- 문서가 한 페이지에 여러 언어로 있으면 앵커(주소 뒤에 붙여 특정 위치로 보내는 #이름)까지 붙여 보낸다. 그냥 열면 맨 위 언어가 나온다
- 문서를 앱에 넣지 않고 링크로 두면 문구를 고칠 때 앱을 다시 배포하지 않아도 된다. 대신 주소가 바뀌면 앱이 깨지므로, 주소는 바꾸지 않기로 정해 두는 편이 낫다
