## 자원을 나눠 주는 규칙

### 우선순위 규칙은 몰림을 만든다

한정된 자원을 순서대로 나눠 주는 구조에서 "이 자원을 먼저 쓴다"는 규칙을 넣으면, 그 자원은 앞쪽 요청에 전부 소진된다. 골고루 쓰이길 바랐다면 정반대의 결과가 나온다.

이 게임에서는 그림 도안을 레벨에 하나씩 배정한다. 정렬 기준이 이랬다.

```python
avail = sorted(SHAPES, key=lambda s: (
    diff[s[0]],                                    # 난이도 순
    0 if s[0] in PROCEDURAL else 1,                # 같으면 직접 만든 것 먼저
    tiebreak[s[0]]))
```

두 번째 줄이 의도였다. 직접 그린 도안이 안 쓰이고 남는 걸 막으려던 것인데, 결과적으로 쉬운 손그림이 앞 레벨에서 다 소진돼 19종 중 15종이 100탄 안에 뭉쳤다.

우선순위는 "쓰이게 하는" 규칙이지 "고르게 쓰이게 하는" 규칙이 아니다. 분포를 원하면 분포를 직접 지정해야 한다.

---

### 고르게 펴려면 자리를 먼저 잡고 난이도로 짝짓는다

간격만 맞춰 기계적으로 배치하면 안 맞는 자리에 들어간다. 이 게임은 레벨마다 목표 난이도가 있어서, 쉬운 도안을 어려운 자리에 넣으면 그 판이 밴드(목표로 잡은 난이도 구간)를 벗어난다.

양쪽을 각자 정렬해 순서대로 붙이면 간격과 적합성을 같이 얻는다.

```python
kr = sorted(korean_shapes, key=lambda n: difficulty[n])   # 도안: 난이도 순
slots = evenly_spaced(1, SPREAD_UNTIL, len(kr))           # 자리: 균등 간격
slots.sort(key=target_difficulty, reverse=True)           # 자리: 목표 난이도 순
for name, slot in zip(kr, slots):                          # 순서대로 짝짓기
    forced[slot] = name
```

결과는 8탄부터 293탄까지 간격 15~16이었고, 억지로 맞지 않는 자리에 들어간 것은 없었다.

### 예약을 했으면 그 자원을 먼저 잠가야 한다

자리를 잡아 주고 돌렸더니 같은 그림이 두 탄에 나왔다. 다섯 종이 그랬다.

원인은 순서였다. 배정 루프는 다른 기준(난이도)으로 도는데, 예약한 슬롯보다 먼저 처리되는 요청이 일반 경로로 같은 자원을 집어 갔다. 그러고 나서 예약 자리에서 또 배정됐다.

```python
# ❌ 예약만 하고 잠그지 않았다 — 먼저 처리되는 요청이 집어 간다
forced[slot] = name

# ✅ 배정 루프 시작 전에 예약분을 통째로 잠근다
forced[slot] = name
used.update(forced.values())
```

예약과 잠금은 한 몸이다. 하나만 하면 예약이 안 지켜진다.

---

### 예약한 것은 재시도에서도 지켜야 사라지지 않는다

이 생성기는 결과가 목표에 못 미치면 다른 자원으로 바꿔 다시 시도한다. 예약한 자리도 그 대상이었다.

문제는 바뀐 자원의 행방이다. 이미 잠겨 있으니 다른 곳에도 못 쓰이고, 원래 자리에서도 빠졌다. 결과물 어디에도 안 나타난다.

```python
pending = [x for x in targets
           if needs_retry(x)
           and not (x in forced and best.get(x) is not None)]
```

만들기 자체가 실패한 경우만 교체 대상에 남기고, 품질이 조금 모자란 것은 그대로 뒀다. 표시되는 난이도는 실측값에 맞춰 다시 붙으므로 결과가 깨지지는 않는다.

예약·잠금·재시도 셋을 같이 보지 않으면 어느 하나에서 자원이 샌다.

## 색을 줄이는 단계에서 벌어지는 일

### 색이 비슷하면 개수가 줄어든다

도안은 배경 말고 최소 세 색이 필요하다. 색이 둘이면 형태가 뭉개져 무엇인지 안 읽히기 때문이다.

흰 백자 그림이 이 조건에 세 번 걸렸다. 원본에는 분명히 세 톤이 있는데, 색을 줄이는 단계에서 두 덩어리로 합쳐진다.

| 원본 | 비율 |
| --- | --- |
| 흰 몸통 | 66% |
| 옅은 그림자 | 21% |
| 진한 그림자 | 10% |

앞 둘의 거리가 54였다. 색 구분 기준(45)은 넘는데도 합쳐진다. 기준을 통과하는 것과 클러스터(색이 뭉쳐 이룬 덩어리)로 살아남는 것은 다른 문제다.

처음 두 번은 가장 가까운 짝을 찾아 고쳐 받았는데, 고칠 때마다 그다음 짝이 걸렸다. 막고 있던 건 거리가 아니라 개수였다.

- 진단할 때는 실패한 조건을 그대로 읽어야 한다. 거리만 보고 개수 조건을 안 봤다
- 흰색·검은색처럼 한쪽에 몰린 그림은 계열이 다른 색을 하나 넣는 게 확실하다. 같은 계열 안에서 톤만 벌리면 계속 합쳐진다

---

### 잔색이 자리를 뺏는다

직접 그린 그림에는 가장자리에 1%짜리 색이 여럿 남는다. 색을 줄이는 알고리즘은 그것들에게도 자리를 배분하므로, 정작 살아남아야 할 주요 색이 자리를 못 받는다.

주요 색으로 스냅해 잔색을 없애면 해결된다.

```python
TARGET = [white, mid, dark, stain]
for each opaque pixel:
    px = nearest(px, TARGET)     # 가장 가까운 주요 색으로
```

한 그림에서 15색이 5색이 됐고, 그제야 원하는 네 색이 살아남았다.

### 큰 그림을 줄여 쓰면 의도가 어디까지 남을지 알 수 없다

게임이 64칸 격자로 그리는데 원본을 250픽셀로 그리면 네 픽셀마다 하나씩만 뽑힌다. 가는 선과 작은 점은 사라진다.

결과 크기로 직접 그리면 보이는 그대로 들어가고, 색 개수와 면적 분포도 그리면서 바로 보인다. 도안 열일곱 종을 그렇게 다시 받으니 열여섯 종이 한 번에 통과했다.

- 그리는 사람에게 "무엇을 그려 달라"보다 "어떤 크기로 그려 달라"가 더 중요할 때가 있다

## 화면

### 글자 외곽선은 같은 글자를 두 번 그린다

밝은 아이콘 위에 흰 글자를 얹으면 안 보인다. 판을 깔면 아이콘을 가린다.

외곽선 속성이 따로 없어서, 같은 글자를 두 번 겹쳐 그린다. 아래는 굵은 선, 위는 채움이다.

```dart
Stack(children: [
  Text(text, style: base.copyWith(
    foreground: Paint()
      ..style = PaintingStyle.stroke
      ..strokeWidth = size * 0.075
      ..strokeJoin = StrokeJoin.round
      ..color = dark,
  )),
  Text(text, style: base.copyWith(color: light)),
])
```

`strokeJoin`을 둥글게 안 하면 글자 모서리에서 선이 뾰족하게 튄다.

### 받은 것은 받은 자리에 적는다

일일 보상에서 무엇을 받았는지는 아이콘으로 보이는데 얼마나 받았는지는 알 수 없었다. 수량은 제목 밑 문구에 분명히 적혀 있었다.

같은 화면에 있어도 시선이 가는 곳에 없으면 없는 것과 같다. 카드가 뒤집히는 동안 눈은 카드에 있지 제목에 있지 않다.
