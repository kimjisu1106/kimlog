오늘은 앞날의 일을 미리 당겨 할 수 있게 만들고, 첫 사용자 피드백을 받아 셋을 반영했다. 새 기술보다는 규칙을 어떻게 가르느냐에서 배운 것이 많았다.

---

## 시간이 지나면 뒤집히는 조건

### 날짜로 가르면 판정이 바뀐다

앞날의 일을 다른 날로 옮기면 원래 날에서 빼야 한다. 처음에는 이렇게 갈랐다.

```ts
// 아직 오지 않은 날에서 옮긴 것은 그날 배치에서 뺀다
const movedOut = record.date > today ? carriedOut.map((c) => c.templateId) : []
```

금요일 일을 목요일로 당긴 상황을 따라가 보니 문제가 보였다. 목요일에는 잘 뜬다. 그런데 금요일이 실제로 오면 그 날은 더 이상 「아직 오지 않은 날」이 아니다. 조건이 반대로 걸리면서, 목요일에 이미 한 일이 금요일에 미완료로 다시 뜬다.

코드는 한 줄도 안 바뀌었는데 판정이 바뀌었다. 조건이 `today`를 보고 있기 때문이다.

### 안 바뀌는 것으로 가른다

같은 구분을 방향으로 다시 썼다.

```ts
export function pulledOut(record: DayRecord): string[] {
  return (record.carriedOut ?? []).filter((c) => c.to < record.date).map((c) => c.templateId)
}
```

`c.to`와 `record.date`는 둘 다 저장된 값이라 시간이 지나도 안 변한다. 오늘이 언제든 같은 답이 나온다.

조건을 쓸 때 「지금」이 들어가면 그 조건은 언젠가 뒤집힌다. 지금이 꼭 필요한 게 아니라면 저장된 것끼리 비교하는 길이 있는지 먼저 봐야 한다.

### 방향이 다르면 남길 것도 다르다

같은 「옮기기」인데 방향에 따라 원래 날에 남기는 것이 달랐다.

- 뒤로 민 것 — 남긴다. 오늘 못 했다는 사실이 사라지면 안 된다
- 앞으로 당긴 것 — 뺀다. 그날이 오기 전에 이미 한 일이라 미완료로 뜨면 거짓말이 된다

처음에는 이 둘을 같은 기능으로 보고 하나로 다뤘다. 데이터 구조는 실제로 하나로 충분했는데(어디서 어디로), 화면에 보여줄 때는 갈라야 했다. 저장하는 모양이 같다고 다루는 방법까지 같은 건 아니다.

---

## 조건을 나열한 순서가 곧 우선순위다

### 자국이 겹치는 날이 생긴다

옮기기는 두 날에 자국을 남긴다. 옮긴 날에 「어디로 보냈다」, 받는 날에 「어디서 왔다」.

목요일로 당겨 놓고 목요일에도 못 하면, 이월이 그 일을 금요일로 되돌려 보낸다. 그러면 금요일 하나가 두 자국을 동시에 들고 있게 된다. 「목요일로 보냈다」와 「어딘가에서 왔다」.

### 먼저 보는 쪽이 이긴다

배치를 짜는 코드가 이렇게 생겼다.

```ts
if (movedOut.includes(t.id)) return false
if (carriedIn.includes(t.id)) return true
```

이 순서면 그 일이 화면에서 통째로 사라진다. 보냈다는 자국을 먼저 보고 빼 버리기 때문이다. 순서를 뒤집었다.

```ts
// 옮겨온 자국이 옮겨나간 자국을 이긴다 — 당겼다가 못 해서 되돌아온 경우가 그렇다
if (carriedIn.includes(t.id)) return true
if (movedOut.includes(t.id)) return false
```

조건을 위에서부터 보는 코드는 순서 자체가 규칙이다. 처음 쓸 때는 하나씩 떠올리며 쓰게 되니 겹칠 일을 생각 안 하는데, 나중에 겹치는 경우가 나오면 순서가 답을 정해 버린다.

### 나중에 생긴 사실이 이긴다

무엇을 앞에 둘지는 「어느 것이 더 나중 이야기인가」로 정했다. 금요일에서 목요일로 보낸 건 먼저 있었던 일이고, 목요일에서 못 해 되돌아온 건 그 뒤의 일이다. 나중 것이 이겨야 지금 상태가 맞다.

같은 판단을 어제 기기 합치기에서도 했다. 거기서는 시각을 찍어 비교했고, 여기서는 순서로 표현했다. 표현이 다를 뿐 규칙은 같다.

### 양쪽에 자국을 남기면 겹침을 반드시 따져야 한다

한 사실을 두 곳에 적으면 두 곳이 어긋나는 경우가 반드시 생긴다. 여기서는 어긋난 게 아니라 둘 다 맞는데 뜻이 반대인 경우였다.

양쪽에 적기로 했으면 「둘이 동시에 있을 때 무엇이 맞나」를 처음부터 정해 두는 게 낫다. 나중에 만나면 이미 만들어 둔 코드 사이에서 찾아야 한다.

## 화면이 다시 그리는 조건

### 정해 놓은 것 밖의 변화는 못 본다

기록실에서 금요일 업무를 옮겼는데 화면이 안 바뀌었다. 저장은 됐다.

기록실은 그 달 기록을 한 번 읽어 들고 있고, 다시 읽는 조건이 이렇게 적혀 있었다.

```tsx
const days = useMemo(() => { ... }, [month, loadMonth, todayDays])
```

달이 바뀌거나, 읽는 함수가 바뀌거나, 오늘 기록이 바뀌면 다시 읽는다. 금요일 기록을 고친 건 셋 중 아무것도 아니다.

여기서 배운 건 이거다. 화면이 무엇을 보고 다시 그리는지를 정해 놓으면 그건 곧 「이것 말고는 안 본다」는 선언이기도 하다. 저장소를 고칠 길을 새로 냈으면 보는 것도 같이 넓혀야 한다.

### 세는 숫자로 다시 읽게 한다

저장소를 고칠 때마다 하나씩 올라가는 숫자를 뒀다.

```tsx
const [revision, setRevision] = useState(0)

// 저장소를 고치고 나서
setRevision((n) => n + 1)

// 읽는 함수가 이 숫자를 본다
const loadMonth = useCallback((m: string) => store.loadMonth(m, visible), [visible, revision])
```

숫자가 바뀌면 함수가 새로 만들어지고, 그 함수를 보고 있던 기록실이 다시 읽는다.

값 자체는 아무 뜻이 없고 「바뀌었다」는 것만 전한다. 저장소처럼 화면 밖에 있는 것이 바뀌었을 때, 바뀐 내용을 다 물려주는 대신 신호만 보내는 방법이다.

### 의존성 목록은 다시 볼 것들의 목록이다

`useMemo`나 `useCallback`의 대괄호 안은 성능 설정이 아니라 「무엇이 바뀌면 다시 하나」를 적는 자리다. 여기에 안 적힌 것은 바뀌어도 화면이 모른다.

- 적어야 할 것을 빼면 — 낡은 화면이 남는다. 오늘 겪은 것
- 필요 없는 것을 넣으면 — 쓸데없이 다시 한다. 느려질 뿐 틀리지는 않는다

둘 중에는 뒤엣것이 낫다. 확신이 없으면 넣는 쪽으로 기운다.

## 스크롤 상자가 어디냐

### 스크롤 상자의 아래 여백은 끝에 안 나타난다

기록실에서 업무가 많으면 마지막 줄이 화면 아래에 딱 붙어 끝나서, 더 없는 줄 알게 된다는 피드백을 받았다.

원인은 우리 앱에 스크롤을 다루는 방식이 두 가지 있었다는 것이다.

- 창고 — 패널 안에 스크롤 상자가 따로 있다. 패널의 아래 여백은 스크롤 밖에 남아 그대로 보인다
- 기록실 — 패널 자체가 스크롤 상자다. 그 여백이 스크롤 안쪽 끝에 안 나타난다

```css
.panel {
  padding: 18px 24px 22px;   /* 이 22px이 */
}

.panel--scroll {
  overflow-y: auto;          /* 여기서는 끝에 안 보인다 */
}
```

### 여백을 내용 안에 둔다

바깥 여백을 손보는 대신 내용의 맨 끝에 빈 자리를 하나 넣었다.

```css
.panel--scroll::after {
  content: '';
  display: block;
  flex: none;
  height: 8px;
}
```

내용이라 반드시 그려진다. 여백이 보이느냐 마느냐를 상자의 성질에 맡기지 않고 직접 정해 두는 쪽으로 옮긴 것이다.

같은 구조를 쓰는 관리와 마을도 이 한 줄로 같이 고쳐졌다. 여러 화면이 같은 이름을 쓰고 있으면 고치는 것도 한 번이다.

### 같아 보이는 두 화면이 다르게 동작한다

창고와 기록실은 화면만 보면 같은 종류다. 둘 다 목록이 있고 스크롤된다. 그런데 스크롤 상자를 어디에 뒀느냐가 달라서 여백이 다르게 나왔다.

같은 일을 하는 곳이 두 가지 방식으로 만들어져 있으면, 한쪽에서만 나는 문제가 생긴다. 그리고 그 문제는 화면을 봐서는 원인이 안 보인다.

## 판단으로 배운 것

### 무언가를 빼면 그 자리에 뭐가 있었는지 본다

상시 업무를 옮기기 대상에서 뺐더니, 그 자리에 원래 있던 「미완료」 글자가 드러났다. 아직 오지도 않은 날에 미완료는 틀린 말이다.

버튼을 없앤 것만 생각하고 그 자리는 안 봤다. 화면에서 무언가를 빼는 변경은 뺀 것뿐 아니라 그 자리에 남는 것까지가 변경이다.

### 같은 값을 두 벌 두면 계속 답해야 한다

업무 순서를 바꿔 달라는 요청이 「오늘과 창고 둘 다」였다. 두 벌로 만들면 이런 질문이 줄줄이 따라온다.

- 오늘 바꾼 순서가 내일도 유지되나
- 창고에서 바꾸면 오늘 것도 바뀌나
- 지난 기록은 그때 순서로 보이나, 지금 순서로 보이나

세 번째가 특히 무겁다. 그때 순서로 보이게 하려면 하루 기록마다 순서를 따로 저장해야 한다.

창고 순서 한 벌만 두고 오늘이 그걸 따라가게 하니 이 질문들이 통째로 없어졌다. 답하기 어려운 질문이 여럿 나오면, 질문을 잘 답하는 것보다 질문이 안 생기게 만드는 쪽을 먼저 본다.

### 요청 한 줄에 결정이 넷 딸려 온다

「업무에 데드라인을 넣어 달라」는 한 줄이었는데, 만들려고 보니 정할 것이 넷이었다.

- 배치에 영향을 주나 — 마감 전까지 매일 뜨나, 원래 날에만 뜨고 마감은 표시만 하나
- 어디에 저장하나 — 반복 업무는 회차마다 마감이 다르니 업무 정의에 두면 안 맞는다
- 지난 마감은 계속 따라오나, 표시만 하나 — 따라오면 이월과 규칙이 겹친다
- 마감 뒤로 넘기려 할 때 막나, 경고하나, 그냥 두나

정하지 않고 만들면 넷을 코드로 아무렇게나 정해 버리게 된다. 그러고 나면 나중에 왜 그렇게 됐는지 아무도 모른다.

### 정할 게 많으면 가장 작게 시작하는 길을 같이 적는다

구상만 적어 두면 다음에 열었을 때 「정할 게 넷이네」에서 또 멈춘다. 그래서 제일 작게 시작하는 길을 함께 적었다.

일회성 업무에만 마감일을 두고 배치에는 영향을 주지 않는다. 오늘 화면에 남은 날짜만 붙인다. 이러면 위 넷 중 셋이 저절로 풀린다 — 정의에 저장, 표시만, 이월과 안 겹침.

미룰 때는 무엇을 정해야 하는지와 함께 어디서부터 손대면 되는지를 남긴다.

### 피드백은 증상이고 원인은 다른 데 있다

「기록실에서 업무가 많으면 스크롤이 딱 끝나 버린다」는 말을 들었다. 화면 이야기로 들리지만 원인은 그 화면이 스크롤을 다루는 방식이었고, 그건 다른 화면과 다르게 만들어져 있었다.

쓰는 사람은 자기가 본 것을 말한다. 그 말을 그대로 고치려 들면 그 자리만 덧대게 된다. 「왜 여기서만 이런가」를 물으면 대개 다른 곳과 다르게 만든 지점이 나온다.

---

여기서부터는 마감을 붙이고, 지운 것이 되살아나던 문제와 자정을 넘기면 날이 갈라지던 문제를 잡으며 배운 것이다.

## 합집합 병합이 못 하는 것

### 없음은 아무 주장도 못 한다

창고에서 업무를 지웠는데 잠시 뒤 다시 나타난다는 말을 들었다.

지우기는 배열에서 빼는 일이고, 두 기기를 합치는 규칙은 양쪽 id의 합집합이다.

```text
1. 지운다              → 이 브라우저 배열에서 빠짐
2. 3초 뒤 자동 동기화  → 드라이브에는 아직 있음
3. 합치기 = 합집합     → 있는 쪽이 이겨서 되살아남
4. 결과를 다시 올림    → 드라이브에도 굳어짐
```

여기서 지움이 지는 이유가 명확하다. 합치기는 「무엇이 있나」를 비교하는데, 지움은 「없다」이므로 비교에 낄 자격이 없다. 나중에 지웠든 아니든 상관없이 늘 진다.

값이 있어야 규칙에 태워진다.

### 지움도 사실로 적는다

배열에서 빼는 대신 「지웠다」는 시각을 찍는다.

```ts
deletedAt?: string
```

그러면 그건 `archived`나 `title`과 다를 게 없는 그냥 값이다. 이미 있는 「나중에 고친 것이 이긴다」 규칙이 그대로 적용된다. 새 규칙을 안 만들어도 된다.

이런 표시를 묘비라고 부른다. 지운 자리에 「여기 있었다」를 남기는 것이다.

### 남겨 두는 게 이득이기도 하다

지운 것을 배열에 남기는 게 어쩔 수 없는 대가처럼 보였는데, 따져 보니 원래 필요했다.

하루 기록은 업무 제목을 복사하지 않고 id로 가리킨다. 그래야 이름을 고쳐도 지난 기록이 따라온다. 그런데 업무를 배열에서 빼 버리면 옛 기록이 가리킬 곳을 잃어 제목이 빈칸이 된다.

지움을 표시로 바꾸면서 이 문제도 같이 없어졌다. 억지로 남기는 게 아니라 남아 있어야 맞는 것이었다.

### 보이는 목록과 저장된 목록을 가른다

묘비를 남기면 저장된 목록과 화면에 세울 목록이 달라진다.

```ts
// 저장은 전부 들고 있고
const templates = store.loadTemplates()

// 화면에 세울 것만 걸러 쓴다
const living = templates.filter((t) => !t.deletedAt)
```

어디서 거르느냐가 중요했다. 배치를 짜는 곳과 창고 목록은 걸러야 하고, 기록실의 제목 찾기는 전체를 봐야 한다. 지운 업무의 옛 기록에도 제목이 떠야 하니까.

「전부 거르기」나 「아무 데서도 안 거르기」가 아니라, 쓰는 자리마다 어느 쪽이 맞는지 따져야 했다.

### 피해가 작다는 판단의 근거를 다시 잰다

이건 동기화를 만들 때 이미 알고 넘어간 한계였다. 문서에 이렇게 적어 뒀다.

> 지움은 표현하지 못한다. 다만 이력이 있는 업무는 완전 삭제가 아니라 보관이라 정상적으로 합쳐지고, 되살아나는 건 한 번도 안 쓴 것뿐이라 피해가 작다.

논리는 맞았다. 틀린 건 「한 번도 안 쓴 것뿐」의 무게였다. 한 번도 안 쓴 업무가 바로 제일 자주 지우는 것이다 — 만들어 보고 아니다 싶어서 지우는 게 그거니까.

한계를 알고 넘어갈 때는 「어떤 경우에 문제가 되나」까지는 대개 맞힌다. 놓치는 건 「그 경우가 얼마나 자주 오나」다. 그건 만들 때가 아니라 써 봐야 안다.

---

## 개념을 나눌 것인가 합칠 것인가

### 차이 하나가 눈에 띄면 거기 맞춰 짓게 된다

마감을 붙이면서 「마감까지」를 일정 종류로 하나 더 만들었다. 반복과 다른 점이 분명했기 때문이다 — 반복은 완료해도 다음 회차에 또 뜨고, 마감은 하면 끝난다.

만들고 나서 「이걸 일 단위 반복으로 해두고 언제까지를 지정하면 되는 거 아니냐」는 말을 들었다.

맞는 말이었다. 반복에 「일」 주기가 있었으면 마감은 그것의 특수한 경우다. 차이는 여전히 하나 있지만, 그 하나 때문에 개념을 새로 만든 셈이었다.

눈에 띄는 차이가 있으면 그게 구조를 가르는 선처럼 보인다. 실제로는 선이 아니라 옵션일 때가 더 많다.

### 특수한 경우인지 새 개념인지 가르는 질문

되짚어 보니 물어야 했던 질문은 이거였다.

- 기존 것으로 표현할 수 있나 — 표현할 수 있으면 특수한 경우다
- 표현하고 나서 남는 차이가 몇 개인가 — 하나면 옵션, 여럿이면 개념

마감은 「N일마다 + 언제까지」로 표현되고 남는 차이가 하나였다. 옵션이 맞았다.

앞서 만든 「일회성」은 다르다. 반복으로 표현하려면 「그날 하루만 반복」이라는 말이 안 되는 규칙이 필요하고, 남는 차이도 여럿이다(회차 개념이 없고, 오늘 화면에서 만들고 지운다). 그건 개념이 맞다.

### 합치면 공짜로 생기는 것이 있다

나눠 뒀을 때 마감은 매일로 고정이었다. 합치고 나니 「9월 1일까지, 3일마다 상기」가 그냥 됐다. 만들려고 한 게 아니라 구조가 그렇게 생겨서 따라온 것이다.

합치는 쪽이 나은지 판단할 때 이걸 같이 본다. 개념 하나가 주는 것과, 합쳤을 때 저절로 생기는 것.

### 구조는 합치고 입구는 남긴다

합치면서 잃는 것도 있었다. 「마감까지」라는 이름이 사라지면 처음 쓰는 사람이 데드라인을 반복 안에서 찾아야 한다.

이건 구조 문제가 아니라 찾는 문제다. 그래서 안쪽은 합치고 입구만 남겼다 — 반복 프리셋에 「마감까지 매일」을 하나 뒀다.

(그 프리셋도 나중에 걷어냈다. 다음 절에 나온다.)

### 틀린 판단은 정정으로 남긴다

문서에서 「마감은 일정 종류다」를 지우지 않고 취소선을 긋고 왜 되돌렸는지를 적었다. 어제 「서버가 필요하다」를 정정한 것과 같은 방식이다.

두 번 해 보니 이 방식의 값어치가 더 보인다. 지워 버리면 다음에 같은 자리에서 「마감을 종류로 만들까?」가 또 떠오른다. 한 번 가 보고 아니었다는 게 적혀 있으면 그 자리에서 멈춘다.

---

## 이름표 대신 값

### 프리셋은 목록에 있는 것만 만들 수 있다

반복 주기를 「매주·격주·매월·3개월마다·매년·직접 정하기」로 고르게 해 뒀었다. 자주 쓰는 것을 앞에 두면 편할 거라고 봤다.

그런데 목록에 없는 것(2일마다, 5주마다)을 만들려면 「직접 정하기」로 한 번 더 들어가야 한다. 이름표가 편한 길이 아니라 갈림길을 만든 셈이다.

숫자와 단위로 바꾸니 그 갈림길이 없어졌다.

```text
[ 1 ] [일마다 ▾]     ← 매일
[ 2 ] [주마다 ▾]     ← 격주
[ 3 ] [개월마다 ▾]   ← 분기
```

이름표로 부르던 것이 전부 이 조합 안에 있다. 이름은 사람이 붙이는 것이지 목록에 있어야 하는 게 아니었다.

### 이름을 값에서 거꾸로 계산하면 되짚다 틀린다

프리셋을 없애니 어제 고친 버그가 원인째 사라졌다.

그 버그는 「직접 정하기」를 골라도 화면이 「격주」로 되돌아가던 것이었다. 원인은 지금 무엇이 켜져 있는지를 값에서 거꾸로 계산한 것이었다 — 2주마다면 격주, 그 외면 직접 정하기.

이름표가 없으면 되짚을 것도 없다. 값이 곧 화면이라 어긋날 자리가 없다.

어제는 「사용자의 의도를 담은 값은 상태여야 한다」로 배웠는데, 오늘은 한 겹 더 갔다. 되짚어야 하는 상황 자체를 안 만들 수 있으면 그게 낫다.

---

## 한 표시가 여러 동작을 정할 때

### 옵션 셋을 하나로 묶기

마감에는 정할 것이 셋이었다.

- 완료하면 그다음 날부터 안 뜬다
- 종료일이 지나도 계속 뜬다
- 뱃지가 주기 대신 남은 날이 된다

셋을 따로 물으면 화면이 지저분해지고, 말이 안 되는 조합도 생긴다(계속 뜨는데 뱃지는 주기인 경우 등). 셋이 사실은 하나의 뜻이었다 — 「이 종료일을 마감으로 다룬다」.

```ts
/** `until`을 「끝나는 날」이 아니라 「마감」으로 다룬다. 셋이 한꺼번에 딸려온다. */
deadline?: boolean
```

옵션이 여럿 나오면 먼저 세어 보는 게 아니라 묶이는지를 본다.

### 묻는 말과 필드 이름이 달라도 된다

화면에서는 「이때까지 못 하면 경고 표시」라고 묻는다. 필드 이름은 `deadline`이다.

쓰는 사람에게는 눈에 보이는 결과(경고가 뜬다)가 제일 또렷하고, 코드에게는 무슨 뜻인지(마감으로 다룬다)가 중요하다. 둘을 억지로 같게 만들면 한쪽이 어색해진다.

대신 필드 주석에 셋을 다 적어 뒀다. 이름만으로 다 담을 수 없으면 이름을 늘리는 것보다 주석이 낫다.

### 반례 하나가 기본값을 정한다

「완료하면 끝」을 옵션으로 두지 말고 항상 켜자는 이야기가 나왔다. 마감이 있는 일은 하면 끝나는 게 당연하니까.

그런데 반례가 하나 있었다. 「매주 월요일 회의, 12월까지」는 종료일이 있지만 첫 월요일에 끝나면 안 된다.

종료일이 있다고 다 마감은 아니다. 반례가 하나라도 있으면 그건 기본값이 아니라 선택이어야 한다.

## 시간에 기대는 상태

### 그릴 때마다 계산되는 값과 한 번 읽은 값이 갈라진다

자정이 지나 도장을 찍었더니 자정 전에 있던 업무들이 사라지고, 도장은 어제 기록에 들어갔다.

```tsx
const today = dateKey()   // 그릴 때마다 다시 계산된다
const [dayMap, setDayMap] = useState(() => /* 열 때 한 번 읽는다 */)
```

이 둘이 같은 날을 가리킨다는 보장이 어디에도 없었다. 자정 전에는 우연히 같았고, 자정을 넘기는 순간 갈라졌다.

- 보드에 세우는 업무 목록 — 새 날짜로 다시 계산 → 어제만 있던 업무가 사라짐
- 도장을 찍어 저장 — 기록 자체는 어제 날짜 → 어제 것에 들어감

「지금」에서 나오는 값을 그릴 때마다 계산하면 시간이 지나며 조용히 바뀐다. 그 값에 기대는 다른 것이 같이 안 바뀌면 어긋난다.

### 날짜를 상태로 두고 확인한다

계산을 상태로 바꿔서 언제 바뀌는지를 우리가 정한다.

```tsx
const [today, setToday] = useState(dateKey())

useEffect(() => {
  const timer = window.setInterval(() => setToday(dateKey()), 30_000)
  return () => window.clearInterval(timer)
}, [])
```

같은 값을 다시 넣으면 React가 알아서 그리지 않으므로, 30초마다 불러도 낭비가 없다. 실제로 바뀌는 건 하루에 한 번뿐이다.

### 왜 자정 타이머가 아니라 간격인가

자정까지 남은 시간을 재서 한 번만 울리게 할 수도 있었다. 더 정확하고 덜 도는데, 컴퓨터가 자면 그 시각이 그냥 지나간다. 깨어나서도 다음 자정까지 안 울린다.

간격은 자고 일어나도 다음 확인 때 따라잡는다. 정확하지 않은 대신 놓치지 않는다.

한 번만 울리는 것과 계속 확인하는 것 중에 고를 때, 놓쳤을 때 어떻게 되는지를 먼저 본다.

### 날이 바뀔 때 같이 돌아야 하는 것들

날짜가 상태가 되니 그것에 기대는 것들을 찾아 붙여야 했다.

- 하루 기록 — 그날 것으로 갈아끼운다
- 이월 훑기 — 어제 못 한 일이 오늘로 와야 하므로 다시 돈다

어제 「화면이 무엇을 보고 다시 그리는지 정해 놓으면 그 밖의 변화는 못 본다」를 배웠는데, 오늘은 반대쪽이었다. 새 신호를 만들었으면 그 신호를 봐야 할 것들을 찾아 이어야 한다.

### 어제를 대신 닫지 않는다

날이 바뀔 때 어제 셔터를 대신 내려 줄 수도 있었다. 안 했다.

하루를 매듭짓는 건 사람이 하는 일이다. 셔터를 내리면 그날 요약이 뜨는데, 자는 사이에 앱이 대신 닫으면 그걸 못 본다. 기록은 맞아도 하려던 것을 못 하게 된다.

자동으로 해 주는 게 늘 친절한 건 아니다. 그 동작에 사람이 볼 것이 붙어 있으면 특히.

## 눌러서 고치는 것

### 누르는 대상이 곧 값이면 값이 빌 때 사라진다

일회성 업무 이름을 눌러서 고치게 해 뒀다. 이름을 잠깐 빈칸으로 뒀더니 그 뒤로 손댈 수가 없었다.

```tsx
<button onClick={() => setEditingId(t.id)}>{t.title}</button>
```

누르는 것은 이름이 적힌 버튼이고, 버튼의 내용이 이름 그 자체다. 이름이 비면 버튼에 글자가 없어 폭이 0이 된다. 누를 것이 사라진 것이다.

값이 곧 조작 대상이면, 값이 빌 수 있는지 반드시 따져야 한다.

### 초안으로 들고 있다가 떠날 때 정리한다

고치는 동안 한 글자씩 저장하고 있었다. 그러니 빈칸도 그대로 저장됐다.

```tsx
const [titleDraft, setTitleDraft] = useState('')

function commitTitle(task: TaskTemplate) {
  const next = titleDraft.trim()
  if (next && next !== task.title) onRename(task.id, next)
  setEditingId(null)
}
```

반복 편집기 숫자 칸에서 쓰던 방식과 같다. 입력 중에는 관대하게 두고, 떠날 때 바로잡는다.

같은 방식이 두 번 나왔다는 건 규칙으로 굳힐 때가 됐다는 뜻이다. 화면에서 고치는 값은 다 이렇게 다루면 된다.

### 막는 것과 되살리는 것은 따로 필요하다

앞으로 안 생기게 막는 것만으로는 이미 빈 이름으로 저장된 업무가 안 고쳐진다. 이미 망가진 건 그대로 남는다.

```tsx
{t.title || '이름 없음'}
```

빈 이름일 때 대신 보여줄 글자를 두니 누를 것이 생겼다.

버그를 고칠 때 두 가지를 나눠 봐야 한다. 앞으로 안 나게 하는 것과, 이미 난 것을 되돌리는 것.

---

## 판단으로 더 배운 것

### 이미 나간 데이터는 고쳐도 저절로 안 낫는다

지움을 고쳤지만, 이미 되살아나서 드라이브에 굳은 것들은 그대로다. 코드가 고쳐졌을 뿐 데이터는 그 전 규칙으로 쓰인 것이라, 새 규칙으로 한 번 더 지워야 한다.

고쳤다고 알릴 때 이걸 같이 말해야 한다. 안 그러면 「고쳤다는데 왜 그대로냐」가 된다.

### 되물으면 설계를 다시 볼 기회다

마감을 종류로 만들었을 때 「이걸 일로 해두고 언제까지를 지정하면 되는 거 아니냐」는 되물음이 왔다. 그 한 마디에 개념 하나가 줄었다.

만든 사람은 만든 순서대로 보게 된다. 마감을 붙이려고 시작했으니 마감이 중심에 있고, 반복은 옆에 있는 다른 것이다. 밖에서 보면 둘 다 「언제 뜨는가」라는 한 덩어리다.

되물음을 방어하지 않고 한 번 따라가 보면, 대개 그 자리에서 뭔가가 줄어든다.
