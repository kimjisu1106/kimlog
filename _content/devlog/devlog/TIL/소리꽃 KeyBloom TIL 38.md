투명(알파) 내보내기를 MP4처럼 워커 풀로 병렬 압축하려 했다. 알파는 투명도를 살려야 해서 손실 압축(JPEG)을 못 쓰고 무손실 PNG라 프레임이 훨씬 무거운데, 4K에서 이게 세 가지 벽으로 나타났다.

---

## 프레임을 통째로 읽으면 메인 힙이 터진다

프레임 픽셀을 워커에 보내려고 `getImageData`로 읽었다. 이건 매번 rgba 버퍼를 새로 할당하는데, 4K는 한 장이 33MB다. 초당 수십 장을 이렇게 할당·해제하면, 전체 여유 메모리가 남아도 33MB 연속 공간을 못 잡아 `Out of memory`가 난다(주소 공간 파편화).

`createImageBitmap`은 캔버스의 스냅샷을 GPU 텍스처 핸들로 만든다 — 메인 힙(자바스크립트 메모리)을 안 먹고, 워커로 넘기는 것도 가벼운 핸들 이전이다.

```ts
// ❌ 매 프레임 33MB(4K)를 메인 힙에 새로 할당 → 파편화로 OOM
const img = ctx.getImageData(0, 0, w, h);
worker.postMessage(img.data.buffer, [img.data.buffer]);

// ✅ GPU 스냅샷 핸들만 넘김 — 메인 힙 안 씀
const bmp = await createImageBitmap(canvas);
worker.postMessage({ bmp }, [bmp]); // 워커에서 drawImage 후 bmp.close()
```

## 워커의 GPU 캔버스는 스레드 간 읽기가 불안정하다

핸들을 넘겼더니 이번엔 워커에서 압축할 때 `NotReadableError`가 났다. 워커가 자기 `OffscreenCanvas`(화면 밖 캔버스)에 그림을 그리고 `convertToBlob`(캔버스를 이미지로)으로 읽는데, 그 캔버스가 GPU 백엔드면 메인 스레드가 만든 GPU 리소스를 워커 스레드에서 읽는 게 브라우저 엔진(WebView2)에서 안정적이지 않다.

캔버스를 만들 때 `willReadFrequently`를 켜면 CPU 백엔드가 된다 — 스레드 간 GPU 문제가 없어 항상 읽힌다.

```ts
// 워커 안 — CPU 백엔드라 convertToBlob이 스레드 넘어도 안전
const ctx = canvas.getContext("2d", { willReadFrequently: true });
```

> 같은 `willReadFrequently`라도 쓰는 이유가 다르다. 리드백을 자주 할 때 속도를 위해 켜기도 하지만, 여기선 "워커 스레드에서 GPU 캔버스를 읽는 오류"를 피하려고 켠다.

## 동시에 다루는 프레임 수는 개수가 아니라 메모리로 제한한다

워커에 한꺼번에 너무 많은 프레임이 나가 있으면 메모리가 부푼다. 처음엔 "동시 N장"으로 개수를 고정했는데, 그 N은 1080p(8MB) 기준이라 4K(33MB)에선 4배가 돼 초과했다.

상한을 개수가 아니라 바이트 예산으로 잡으면, 프레임이 크면 자동으로 적게 물린다.

```ts
const frameBytes = width * height * 4;      // 1080p=8MB, 4K=33MB
const cap = Math.max(2, Math.floor(BUDGET / (frameBytes * 2)));
```

이렇게 해도 4K는 근본적으로 무거워, 4K는 이 웹 기반 경로 대신 별도 앱으로 미루고 현 앱은 1080p로 확정했다.

투명(알파) 내보내기용으로 처음엔 Ut Video를 썼는데, 결과 파일을 편집툴에서 열려면 시청 PC에 코덱을 따로 깔아야 하는 마찰이 있었다. 베가스·프리미어·다빈치가 설치 없이 바로 읽는 투명 영상은 사실상 ProRes 4444라, 거기로 일원화했다.

---

## 코덱을 바꾸는 건 ffmpeg 인자 하나

우리는 프레임을 ffmpeg의 표준 입력(stdin)으로 흘려보내고, ffmpeg가 인코딩·먹싱을 한다. 그래서 코덱을 바꾸는 건 출력 인자만 갈아끼우면 된다 — 렌더 쪽은 그대로다.

```text
# Ut Video (구): 무손실 RGBA, 근데 코덱 설치 필요
-c:v utvideo -pix_fmt gbrap

# ProRes 4444 호환 (신): 편집툴 네이티브, 알파 포함
-c:v prores_ks -profile:v 4444 -pix_fmt yuva444p10le
```

- `prores_ks` = ffmpeg의 ProRes 인코더
- `-profile:v 4444` = 알파(투명)를 담는 ProRes 프로파일
- `yuva444p10le` = 알파 채널(`a`)이 있는 10비트 픽셀 포맷

입력은 PNG 프레임을 stdin으로 받게 `-f image2pipe`로 열어, 프레임을 디스크에 수천 장 안 쓰고 바로 흘려보낸다.

## 표기는 "ProRes 호환(via FFmpeg)"으로

ffmpeg의 ProRes는 Apple의 정식 인코더가 아니라 독자 구현이다. 특허·상표 회색지대라, 실무 호환엔 문제없지만 "Apple ProRes" 배지나 전면 마케팅 문구는 피하고 "ProRes 호환" 정도로 표기하는 게 안전하다.

> 리스크를 완전히 없애려면 대안도 있다 — 공연 업계 표준이고 완전 오픈인 HAP 알파, 또는 코덱 무관한 PNG 시퀀스. macOS 빌드를 만들면 OS 정식 인코더(VideoToolbox)로 완전 합법적인 ProRes를 쓸 수 있다.

## 게이트를 하나로 묶으면 나중에 못 쪼갠다

처음엔 워터마크 제거·4K·알파를 하나의 유료 판정으로 다 잠갔다. 그런데 정책이 "알파는 유료로 열고, 4K는 이 앱에선 아예 안 연다(별도 앱)"로 바뀌자, 하나로 묶인 게이트로는 4K만 따로 뺄 수가 없었다.

판정을 기능별로 분리하니 티어를 자유롭게 조정할 수 있었다.

```ts
// ❌ 하나로 묶으면 4K만 따로 못 뺌
if (!isPro() && (height >= 2160 || alpha)) return;

// ✅ 분리 — 4K는 티어 무관 잠금, 알파는 라이선스
if (height >= 2160) return;      // 4K는 어느 티어에도 안 열림
if (!isPro() && alpha) return;   // 알파는 유료면 열림
```

## 정규식에 넣은 제어문자 범위가 소스에 널바이트로 박혔다

출력 파일명에서 금지문자를 지우는 정규식에, 제어문자(코드 0x00~0x1F)까지 지우려고 그 범위를 유니코드 이스케이프로 넣었다. 그런데 편집 과정에서 그 이스케이프가 문자 그대로의 제어 바이트(널바이트 등)로 소스 파일에 박혀버렸다. 그 순간 파일이 "바이너리"로 취급돼 `grep`·`sed`·에디터가 그 줄을 제대로 못 다뤘다(편집이 왜 안 먹히는지 겉보기로는 잘 안 드러난다).

텍스트 입력엔 제어문자가 거의 없으니, 범위를 빼고 파일시스템 금지문자만 지우니 해결됐다.

```ts
// 금지문자만 지움(제어문자 범위는 안 넣음) — 공백·하이픈은 유지
const s = name.replace(/[\\/:*?"<>|]/g, "");
```

> 증상이 "grep이 Binary file matches라고만 뜨고 내용을 안 보여줌"이면 그 파일에 널바이트가 박힌 것이다. `tr -cd '\000' < 파일 | wc -c` 로 널바이트 개수를 셀 수 있다(0이 아니면 박힌 것).

## 파일 쓸 때 하위폴더는 자동으로 만든다

PNG 시퀀스는 파일이 수천 개라 이름별 하위폴더로 정리하고 싶었다. 근데 파일 쓰기 함수(`std::fs::write`)는 상위 폴더가 없으면 실패한다. 쓰기 전에 부모 경로를 만들어 주면 된다.

```rust
if let Some(parent) = std::path::Path::new(&path).parent() {
    let _ = std::fs::create_dir_all(parent); // 없으면 만들고, 있으면 무시
}
std::fs::write(&path, bytes)?;
```

---

참고한 앱과 다른 결을 만들려고 새 파티클 모드 "모래 유영"을 짰다. 목표는 — 노트마다 건반에서 작은 모래알들이 태어나 (1) 한 무리로 뭉쳐 세로 컬럼 안에서 (2) 각자 자유롭게 흩날리며 오르기. 이 "무리로 뭉치되 개별로 자유롭게"가 생각보다 까다로웠다.

## 시도 1 — 공유 흐름장: 무리가 링처럼 돈다

처음엔 화면에 흐름장(보이지 않는 물결 벡터장)을 깔고 파티클을 태웠다. 뭉치지 않고 유기적으로 흐르라고 "발산 없는(divergence-free) 흐름장"까지 썼다 — 파티클이 한 점으로 빨려들거나 뿜어지지 않고 소용돌이로만 흐르는 장.

근데 한 노트의 파티클들은 좁은 무리라 다들 거의 같은 위치에 있고, 같은 위치는 흐름장 값이 거의 같다. 그래서 다 같은 방향으로 움직여 — 모래가 아니라 담배 연기 도넛처럼 다 같이 도는 링이 됐다.

---

## 시도 2 — 중심으로 당기기: 그것도 링

무리를 뭉치려고 "그룹 중심으로 당기는 힘(스프링)"을 넣었더니, 파티클들이 중심에서 일정 반경에 깔려 또 링이 됐다. 점으로 당기는 힘은 필연적으로 그 점 주위에 껍질(반경)을 만든다.

게다가 스프링은 관성이 있어서, 화음을 치면 여러 무리가 동시에 뭉쳤다 퍼지는 펄스로 출렁였다(동시에 태어난 애들이 같은 시계로 움직여서).

---

## 시도 3 — 딱딱한 경계: 가장자리에 벽이 쌓인다

세로 컬럼을 유지하려고 "폭을 넘으면 되돌림"으로 좌우를 가뒀다. 그랬더니 최대폭에 닿은 알갱이들이 좌우 가장자리에 두 줄로 멈춰 쌓여 벽이 됐다(실기 스크린샷으로 확인). 딱딱한 벽은 거기 닿은 것들을 그 자리에 세운다.

---

## 답 — 개별 난류 + 유계 진동

세 번의 실패에서 공통점을 봤다. 좁은 무리를 "공유 규칙"으로 움직이면 획일적이 된다. 그래서 공유를 버렸다.

각 파티클에 서로 다른 위상의 진동 2개(비례하지 않는 주파수)를 합성한 독립 난류를 줬다. 각자 제 리듬이라 링·획일화·집단 펄스가 한 번에 사라졌다.

```ts
// 파티클마다 다른 위상 → 같은 자리라도 다른 방향. 공유 field 아님
const w1 = time * F1 + p.swayPhase;
const w2 = time * F2 + p.flowPhase;
const wander = Math.sin(w1) + 0.5 * Math.sin(w2 * 1.3);
```

가로 컬럼은 "넘으면 되돌림"(벽) 대신, 밴드 안에서 늘 좌우로 살랑거리는 유계 진동을 목표로 부드럽게 따라가게 했다. 값이 항상 밴드 안이라 가장자리에 멈출 일이 없어 벽이 안 생기고, 파티클마다 위상이 달라 컬럼을 고르게 채운다.

```ts
// 목표 x가 항상 ±밴드 안(유계) → 벽에 안 쌓임. 위상이 파티클마다 달라 제각각
const hx = Math.sin(time*F1*1.3 + p.swayPhase)*0.6 + Math.sin(time*F2 + p.flowPhase*1.7)*0.4;
p.x += (p.baseX + hx * BAND - p.x) * Math.min(1, HSMOOTH * dt);
```

무리로 뭉치는 것(같은 컬럼·같은 상승)은 공유하되, 그 안의 움직임은 철저히 개별 — 이게 모래 느낌이었다.

## 요약

- `getImageData`는 프레임마다 큰 버퍼를 새로 할당해 4K에서 파편화 OOM → `createImageBitmap`(GPU 핸들)로 메인 힙을 안 쓴다
- 워커의 GPU 캔버스는 스레드 간 `convertToBlob`이 `NotReadableError`가 날 수 있다 → `willReadFrequently`(CPU 백엔드)로 안정화
- 동시 프레임 상한은 개수가 아니라 메모리 예산으로 잡아야 해상도가 커져도 안 터진다
- 편집툴이 설치 없이 바로 읽는 투명 영상 = 사실상 ProRes 4444
- 프레임을 ffmpeg stdin으로 흘리는 구조면 코덱 교체는 `-c:v` 인자 하나 (`prores_ks -profile:v 4444 -pix_fmt yuva444p10le`)
- ffmpeg ProRes는 비인증 구현이라 "ProRes 호환"으로 표기 — Apple 배지·마케팅은 피하기
- 유료 게이트를 하나로 묶으면 티어를 못 쪼갠다 → 기능별로 분리해야 정책 변경에 유연
- 정규식에 제어문자 범위를 유니코드 이스케이프로 넣으면 소스에 널바이트가 박혀 파일이 바이너리 취급될 수 있다 → 텍스트 입력엔 금지문자만
- 파일 쓰기 전에 `create_dir_all(parent)`로 하위폴더를 자동 생성
- 좁은 무리를 공유 규칙(흐름장·중심 스프링)으로 움직이면 다 같이 돌아 링·획일화가 된다
- 점으로 당기면 반경 껍질(링), 딱딱한 경계는 닿은 것들을 세워 벽 → 둘 다 인위적
- 답은 파티클마다 독립적인 난류(비례 안 하는 위상 진동) + 유계 진동으로 가두기 — 뭉침은 공유하되 움직임은 개별
