오늘은 지나간 날 기록을 고칠 수 있게 방을 하나 더 열었다. 그 방 하나 때문에 여기저기서 전제가 깨졌는데, 깨진 자리들이 다 비슷한 모양이었다.

---

## 상태를 여러 개 같이 바꿀 때

### 바뀌면 닫는다와 안 맞으면 닫는다는 다르다

기록실에서 다른 가게의 날짜를 누르면 그 가게로 옮겨가면서 그날 보드를 연다. 만들어 놓고 눌러 보니 방이 열리자마자 닫혔다.

원인은 이 규칙이었다.

```tsx
// 가게가 바뀌면 열어 둔 지난 날은 남의 가게 것이 된다
useEffect(() => {
  setPastDate(null)
  setPastDay(null)
}, [activeSpace?.id])
```

규칙 자체는 맞다. 다른 가게로 걸어가면 열어 둔 남의 날짜는 닫혀야 한다. 그런데 이번에는 여는 과정에서 가게가 바뀌었다. 열려고 옮겨간 건데 규칙은 그걸 「바뀜」으로 세고 닫아 버렸다.

조건을 다시 썼다.

```tsx
// 지금 가게와 안 맞으면 닫는다
useEffect(() => {
  if (pastDay && activeSpace && pastDay.spaceId !== activeSpace.id) {
    setPastDate(null)
    setPastDay(null)
  }
}, [activeSpace?.id, pastDay])
```

닫을 이유는 「무언가 바뀌었다」가 아니라 「지금 둘이 안 맞는다」였다. 앞엣것은 변화를 세는 것이고 뒤엣것은 상태를 보는 것이다.

### 자기가 시작한 변화를 자기가 취소한다

이 버그의 모양이 재미있었다. 여는 동작이 스스로를 취소했다.

```text
1. 누른다 → 가게를 옮기고, 날짜를 열고, 그 방으로 간다
2. 가게가 바뀜 → 「가게가 바뀌었으니 열어 둔 날짜를 닫자」
3. 닫힘
```

변화를 감시하는 코드는 그 변화가 어디서 왔는지 모른다. 밖에서 온 것이든 자기 쪽에서 낸 것이든 똑같이 보인다. 그래서 「이런 일이 생기면 저걸 되돌린다」는 규칙을 쓸 때는, 그 「이런 일」을 일부러 내는 경우가 있는지 먼저 봐야 한다.

상태를 보는 조건으로 쓰면 이 문제가 없다. 상태에는 출처가 안 적혀 있고, 애초에 볼 필요도 없다.

### 목록 하나를 여러 곳이 같이 본다

지난 날 방이 생기면서 탭에는 방이 넷인데 거리 끄트머리는 셋으로 알고 있었다. 그래서 기록실에서 오른쪽 끄트머리를 눌러도 새 방으로 못 갔다.

두 곳이 각자 세고 있었기 때문이다.

```tsx
// 탭
[...ROOMS, ...(pastDate ? [shortDate(pastDate)] : [])].map(...)

// 끄트머리
{room < ROOMS.length - 1 && <button ... />}
```

목록을 한 번만 만들어 둘 다 그걸 보게 했다.

```tsx
const rooms = pastRoom && pastDate ? [...ROOMS, shortDate(pastDate)] : ROOMS
```

같은 것을 두 곳에서 세면 처음에는 맞는다. 어긋나는 건 늘 나중에 하나가 늘 때다.

### 화면에 실제로 있는 것만 목록에 넣는다

위 코드에서 `pastRoom &&`이 붙은 이유가 있다. 처음에는 `pastDate`만 봤는데, 날짜는 정해졌지만 방은 아직 안 세워지는 짧은 순간이 있었다.

그러면 탭은 넷인데 갈 곳은 셋이라, 네 번째 탭을 눌러도 아무 일이 안 난다. 눌리는데 아무 일도 안 나는 건 안 눌리는 것보다 나쁘다 — 고장인지 원래 그런지 알 수가 없다.

목록의 기준을 「열기로 했나」에서 「실제로 서 있나」로 바꿨다.

## 기준점이 되는 값

### 시작일은 끝을 정하는 값이 아니었다

반복에 종료일을 붙일 때 「계속 / 언제까지」로 물었다. 끝을 정하는 것이니 끝만 물으면 된다고 봤다.

그런데 「2주마다」는 어디서부터 세느냐에 따라 뜨는 날이 달라진다. 시작일이 그 기준점이다. 그걸 만든 날로 고정해 두고 안 보여주니, 격주 업무가 왜 하필 이 목요일에 뜨는지 설명할 방법이 없었다.

「계속 / 기간」으로 바꾸고 기간을 고르면 시작일과 종료일을 함께 정하게 했다. 물어보는 것이 하나 늘어난 게 아니라, 원래 있어야 할 것이 빠져 있었다.

### 안 보이면 설명이 안 되는 값은 고칠 수 있어야 한다

값이 화면에 있어야 하는지 판단할 때 쓸 기준이 하나 생겼다.

- 그 값을 모르면 화면에 보이는 결과를 설명할 수 없나 — 그러면 보여야 한다
- 값이 바뀌면 결과가 바뀌나 — 그러면 고칠 수 있어야 한다

시작일은 둘 다 해당됐다. 그런데 만들 때는 「끝을 정하는 기능」이라고 이름 붙였기 때문에 시작은 딸린 값처럼 보였다. 기능에 붙인 이름이 무엇을 보여줄지까지 정해 버린 셈이다.

### 읽는 순서가 기준부터 와야 한다

미리보기 문구도 같이 고쳤다.

```text
매주 목 · 2027.08.27까지          (전)
2026.08.27~2027.08.27 · 매주 목   (후)
```

「매주 목」을 먼저 읽으면 어느 목요일인지 모른 채로 읽게 된다. 기간이 먼저 오면 그 안에서 매주라는 게 읽힌다.

화면에 무엇을 넣을지 정하고 나면 순서를 한 번 더 봐야 한다. 다 넣었는데 안 읽히는 경우가 있다.

## 도구를 쓰다 낸 사고

### 설정 없이 돌린 도구는 자기 기본값을 쓴다

들여쓰기를 맞추려고 코드 정리 도구를 한 번 돌렸다. 고친 건 세 줄인데 바뀐 줄이 육백 줄이 됐다. 따옴표와 세미콜론까지 프로젝트와 다른 방식으로 통째로 바뀌었다.

도구는 프로젝트 규칙을 모른다. 설정 파일이 없으면 자기 기본값을 쓰고, 그 기본값이 프로젝트와 다르면 전부 자기 쪽으로 끌어당긴다.

되돌리고 손으로 들여썼다. 세 줄을 고치려고 도구를 들이는 건 애초에 과했다.

### 공백을 빼고 비교하면 진짜 바뀐 줄만 보인다

되돌린 뒤 손으로 들여쓰고 나니 여전히 바뀐 줄이 백팔십 줄이었다. 들여쓰기가 한 단계 밀린 것까지 다 세어졌기 때문이다.

```bash
git diff -w
```

공백 차이를 빼고 보니 실제로 바뀐 건 세 줄이었다.

큰 변경 뒤에 「의도한 것만 바뀌었나」를 확인할 방법이 있어야 한다. 없으면 확인을 포기하게 되고, 포기한 자리에 사고가 숨는다.

## 무엇을 막고 무엇을 열어 둘까

### 앱이 낸 오류를 사람이 못 고치게 두는 건 결함이다

지난 날 기록을 고칠 수 있게 할지 고민했다. 열면 「기록」이라는 말이 흔들리고, 안 열면 잘못 들어간 것이 영영 남는다.

결정을 밀어 준 건 이 한 가지였다. 어제 자정을 넘겨 찍힌 도장이 어제 기록에 들어간 건 사람이 잘못 누른 게 아니라 날짜가 어긋나게 짜여 있던 탓이었다. 코드는 고쳤지만 이미 들어간 도장은 그대로 남았다.

앱이 낸 오류를 사람이 못 고치게 두면, 고쳤다고 말해도 그 사람 화면에서는 안 고쳐진 것이다.

### 범위를 자르는 선에 근거가 없으면 안 자르는 게 낫다

「어디까지 거슬러 올라가 고칠 수 있게 할까」를 한참 봤다. 어제만? 이번 주? 일주일?

어떤 선을 골라도 근거를 못 댔다. 일주일로 하면 팔 일 전 것에서 막히는데, 팔 일과 칠 일 사이에 아무 차이가 없다. 선을 그으면 그 선을 설명해야 하고, 설명 못 하는 선은 그냥 불편이다.

안 잘랐다. 대신 자르지 않아서 생기는 것을 하나 받아들였다 — 달력 칸 색이 사후에 바뀔 수 있다.

### 자기 일지와 감사 기록은 다르다

받아들일 수 있었던 이유가 이거였다.

이 앱의 기록은 볼 사람이 자기뿐이다. 남에게 보이거나 심사를 받는 기록이 아니다. 그러면 「나중에 고쳐서 예뻐 보이게 만들 수 있다」는 게 문제가 아니다. 스스로를 속이는 건 앱이 막을 문제가 아니다.

무엇을 막을지 정할 때 「누가 이걸 보나」를 먼저 물으면 답이 줄어든다. 보는 사람이 자기뿐이면 막을 것이 거의 없다.

### 하나를 늘려 보기 전에는 안 보이는 하드코딩이 있다

방을 하나 더 붙였더니 세 군데가 한꺼번에 드러났다. CSS에 방 번호가 하나씩 적혀 있었고, 탭과 거리 끄트머리가 개수를 따로 세고 있었고, 방으로 가는 코드에 맨 숫자가 박혀 있었다.

셋 다 방이 셋일 때는 아무 문제가 없었다. 그래서 안 보였다.

- 「지금 몇 개인가」에 맞춰 쓴 코드는 그 개수에서는 완벽하게 동작한다
- 하나 늘려 보기 전에는 그게 굳은 건지 유연한 건지 알 수 없다

마감을 반복 안으로 합쳤을 때도 비슷했다. 늘려 보거나 합쳐 보는 것이 설계를 확인하는 방법이다. 머리로만 보면 지금 모양이 늘 맞아 보인다.
