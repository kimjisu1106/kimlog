운영자가 손을 떼도 팀이 돌아가게, 계정·권한 관리 일부를 다른 사람에게 넘기는 작업을 했다. 그 과정에서 배운 것들을 모았다.

---

## 전체를 열지 말고, 필요한 문만 따로 낸다

관리자 전용 기능이 통째로 한 관문(역할이 관리자인가)으로 막혀 있었다. 그중 일부 동작만 남에게 넘기려니, 그 관문을 느슨하게 풀면 나머지 관리 기능까지 다 열린다. 그래서 관리자 라우터는 그대로 두고, 넘길 수 있는 동작만 별도 라우터로 빼서 "그 권한을 가진 사람" 관문을 새로 걸었다. 관리자도 그 관문을 통과하므로 두 곳이 같은 엔드포인트를 공유한다.

```ts
// 관리자 전용 라우터 — 그대로 관리자만
admin.use("*", (c, next) =>
  c.get("user").role === "admin" ? next() : c.json({ error: "forbidden" }, 403),
);
// 넘길 수 있는 동작만 별도 라우터 — 권한 보유자면 통과(관리자 포함)
approvals.use("*", (c, next) =>
  isApprover(c.get("user")) ? next() : c.json({ error: "forbidden" }, 403),
);
```

권한을 넓히고 싶을 때 기존 문을 넓히지 말고, 좁은 문을 새로 내는 게 안전하다.

---

## 줄 수 있는 건 자기가 가진 것까지만

넘겨받은 사람이 남에게 권한을 줄 때, 자기도 없는 권한을 주면 권한이 새어 나간다. 그래서 부여자가 그 권한을 실제로 가졌는지 서버가 검사한다(관리자는 늘 통과). 그리고 어떤 권한이냐를 요청 값으로 받아 컬럼을 고치는데, 받은 값을 그대로 컬럼명에 쓰면 위험하니 미리 정한 목록(화이트리스트)에 있는 것만 허용했다.

```ts
const PERM_HAS = { can_a: isA, can_b: isB }; // 권한 → 보유 검사 맵
if (!(perm in PERM_HAS)) return bad; // 목록 밖이면 거부
if (!PERM_HAS[perm](actor)) return forbidden; // 자기가 가진 것만
// perm은 위에서 검증됐으므로 컬럼명으로 안전
await db.prepare(`UPDATE users SET ${perm} = ? WHERE id = ?`).bind(value, id);
```

"자기가 가진 범위 안에서만 위임"은 한 줄 검사로 된다. 동적 컬럼명은 화이트리스트가 곧 방어다.

---

## 임시 정지와 관계 종료는 다른 상태다

계정을 못 쓰게 하는 방법은 이미 있었다(잠금). 그건 "잠깐 막음, 되돌릴 수 있음"이다. 그런데 "떠남"은 성격이 다른데 같은 잠금으로 갈음하면 목록에서 구분이 안 된다. 그래서 별도 상태(탈퇴)를 뒀다. 계정 줄을 지우는 하드 삭제는 안 했다 — 그 사람이 남긴 데이터가 주인을 잃기 때문이다. 로그인만 영구 차단하고, 데이터는 남기고, 필요하면 되돌린다. 상태 컬럼이 자유 문자열이라 값 하나 늘리는 걸로 끝나 스키마 변경도 없었다.

상태의 뜻을 뭉뚱그리지 말고, 다르면 다른 값으로 나눈다.

---

## 권한 하나 추가는 정해진 한 세트로 움직인다

권한 플래그를 새로 하나 넣으니 손댈 곳이 늘 같은 세트였다 — DB 컬럼, 보유 판정 헬퍼, 로그인 응답, 서버 관문, 화면 토글. 기존 권한들과 똑같은 모양으로 배선하면 빠뜨림 없이 붙는다. 관리자는 모든 판정 헬퍼에서 늘 참으로 쳐서 예외를 안 만든다.

```ts
export function isX(u) {
  return u.role === "admin" || !!u.can_x;
}
```

반복되는 확장은 "이미 있는 패턴을 그대로 따른다"가 가장 안전하다.

---

## 권한 경계는 화면 경계와 같이 간다

넘겨받은 사람에게 관리자 화면 전체를 보여주면, 그가 못 하는 기능까지 눈에 띄어 실수·오해가 생긴다. 그래서 그 사람에겐 필요한 기능만 담은 별도 화면을 따로 만들었다. 서버에서 막는 것과 별개로, 화면에서도 할 수 있는 것만 보이게 한다.

서버 관문이 진짜 방어지만, 화면을 권한에 맞춰 좁히면 사용자가 헷갈리지 않는다.

---

## 이미 들어와 있는 사람의 상태가 도중에 바뀌면

로그인해 쓰고 있는 사람을 도중에 내보내면(탈퇴·잠금) 쿠키는 아직 살아 있다. 하지만 데이터 요청은 "정상 상태의 세션만" 통과하는 관문을 지나므로, 그 순간부터 기능이 막히고 다음 로그인 때 안내 화면으로 간다. 차단을 동작마다 심지 않고 관문 한 곳에서 상태로 판정하면, 이런 도중 변경 엣지가 저절로 닫힌다.

---

## 합칠 중복과 놔둘 중복을 가른다

두 화면에 같은 게 여럿 있었다. 상태 라벨 맵·작은 유틸 함수는 구조 차이가 0이라 한 곳으로 뺐다(순이득). 반면 상태별 버튼 묶음은 겹쳐 보여도 두 화면의 그릇이 달라, 공용 컴포넌트로 묶으면 화면마다 분기 값을 넘겨야 해서 추상화가 샌다 — 실익 대비 위험이 커 안 했다. 대신 딱 하나, 두 곳에 똑같던 확인 문구만 상수로 뺐다(진짜 어긋날 위험은 그것뿐).

중복이라고 다 합치는 게 아니다 — 구조가 같으면 합치고, 다르면 놔둔다.

---

## 기능을 더하면 설명서도 같은 흐름에서

기능을 여러 개 붙였는데 사용자 설명서가 옛날 그대로면 새 기능은 아무도 모른다. 코드와 설명이 갈라지지 않게, 기능이 어느 정도 모이면 설명서도 같은 작업 흐름에서 갱신했다.

설명서는 기능의 일부다 — 코드만 최신이고 설명이 뒤처지면 그 기능은 반쯤만 있는 셈이다.

---

## 요약

- 권한을 넓힐 땐 기존 문을 넓히지 말고 좁은 문을 새로 낸다(관리자 라우터는 그대로, 넘길 동작만 별도 관문).
- 위임 부여는 "자기가 가진 권한까지만" 한 줄로 검사. 동적 컬럼명은 화이트리스트가 방어.
- 임시 정지(잠금)와 관계 종료(탈퇴)는 다른 상태로. 하드 삭제 대신 소프트 상태로 데이터 보존·되돌리기.
- 권한 하나 추가는 컬럼 + 헬퍼 + 로그인 응답 + 관문 + 화면 토글 한 세트를 기존 패턴대로.
- 권한 경계에 맞춰 화면도 좁힌다.
- 차단은 관문 한 곳에서 상태로 — 세션 중 상태 변경 엣지가 저절로 닫힌다.
- 구조 같은 중복만 합치고, 구조 다르면 놔둔다. 완전 동일한 리터럴만 상수화.
- 기능을 더하면 사용자 설명서도 같이 갱신한다.
