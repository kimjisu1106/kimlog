콘티에 담은 곡을 절 단위로 골라·반복·재배열하는 기능을 붙였다. 배치(순서)만 저장하고 가사 내용은 곡을 계속 참조한다. 그 과정에서 걸린 것들.

---

## 예약만 돼 있던 컬럼을 실제로 살리기

이 배치를 담을 컬럼(`lyrics_override`)은 스키마엔 처음부터 있었지만 코드 어디서도 안 쓰였다. "자리는 있으니 쓰면 된다"고 가볍게 봤는데, 컬럼 하나를 실제로 살리려면 데이터가 지나는 길을 전부 이어야 했다.

- 읽기: 상세 조회 SELECT에 컬럼 추가 + 응답 DTO(화면·서버가 주고받는 데이터 꾸러미)에 넣기
- 저장: 항목 저장 INSERT에 컬럼 추가
- 복사: 콘티 복제·순서지에 콘티 넣기의 `INSERT ... SELECT`에도 컬럼 추가(안 하면 배치가 복사 때 조용히 사라진다)
- 모델: 클라이언트 타입 + 로드 매핑
- 내보내기: PPT 만들 때 그 값을 실제로 소비

한 군데라도 빠지면 저장은 되는데 안 보이거나, 복사하면 사라지는 식으로 반쯤만 동작한다. 그리고 미리보기는 따로 손 안 댔는데도 됐다 — 슬라이드를 만드는 순수 함수 하나를 미리보기와 PPT가 이미 공유하고 있어서, 거기만 배치를 반영하니 둘 다 따라왔다.

나중에 곡별 메모를 붙일 때도 예약만 돼 있던 다른 컬럼을 같은 다섯 갈래로 이었는데, 여기선 함정이 하나 더 있었다. 이 앱의 콘티 저장은 "항목 전부를 지우고 다시 넣기"라, 메모에 "누가 썼는지"를 담으면 통째 저장 때마다 그 값이 날아갈 수 있다. 작성자를 서버가 다시 정하면 전부 마지막에 저장한 사람으로 뭉개진다. 그래서 각 항목의 작성자를 화면 쪽이 계속 들고 다니다가 저장 때 그대로 돌려보내고, 내가 고친 항목만 내 이름으로 바꿔 보냈다. 저장은 통째로 해도 작성자는 항목마다 따로 남는다.

## 절은 빈 줄로 나누고, 배치는 원본 줄 번호로 편다

절은 가사를 빈 줄로 나눈 블록으로 잡았다(자동으로 절/후렴을 판정하지 않고 사용자가 블록을 배치). 배치는 블록 인덱스의 순서, 예를 들어 `[0,1,2,1]`이면 1절·후렴·2절·후렴이다.

문제는 줄별 스타일이었다. 이 앱은 넘치는 줄의 글자 크기를 줄여 저장하는데, 그 값이 "원본 곡의 몇 번째 줄"로 키가 걸려 있다. 블록을 반복·재배열하면 출력 순서와 원본 줄 번호가 어긋나므로, 편 결과의 각 슬라이드에 원본 곡의 전역 줄 번호를 함께 달아 그 번호로 스타일을 찾게 했다.

```ts
export function arrangedLines(lyrics, arrangement) {
  let g = 0;
  // 각 줄에 원본 곡에서의 전역 번호 gi를 붙인다
  const blocks = lyricBlocks(lyrics).map((bt) => lyricLines(bt).map((text) => ({ text, gi: g++ })));
  const order = arrangement?.length ? arrangement : blocks.map((_, i) => i);
  return order.filter((bi) => bi >= 0 && bi < blocks.length).flatMap((bi) => blocks[bi]);
}
// 슬라이드 만들 때: style = line_styles[gi]  (출력 위치가 아니라 원본 줄 기준)
```

배치가 없으면 전체 순서(현재 동작)이고, 범위 밖 인덱스는 걸러진다.

---

## 인덱스 범위만으론 "절이 늘어난 것"을 못 잡는다

배치가 가리키는 블록이 사라지면(절이 줄면) 인덱스가 범위를 벗어나니 "다시 확인하라"고 띄울 수 있다. 그런데 절이 늘어난 경우는 인덱스가 다 유효해서 안 잡힌다 — 그냥 두면 새로 생긴 절이 그 콘티에서 조용히 빠진다.

인덱스만 봐선 "구조가 그대로인지"를 알 수 없다는 게 핵심이었다. 그래서 배치를 저장하는 순간의 절 개수 `n`을 함께 저장했다.

```ts
// 저장: 그 시점의 절 개수를 스냅샷으로
{ n: lyricBlocks(song.lyrics).length, order: [0, 1, 2, 1] }
// 판정: 지금 절 개수가 n과 다르면(늘든 줄든) '재조정'
const stale = arrangement.n !== lyricBlocks(song.lyrics).length;
```

구조의 스냅샷(여기선 개수)을 하나 들고 있으면, 이후 변화가 어느 방향이든 감지된다.

## 곡이 바뀌면 콘티를 통째로 리로드하지 않고 곡만 갈아끼운다

곡을 편집해 절 개수가 바뀌면 열려 있는 콘티에 '재조정'이 바로 떠야 자연스럽다. 그런데 콘티가 들고 있는 곡 정보는 콘티를 열 때 한 번 읽은 것이라, 곡을 고쳐도 갱신되지 않았다.

가장 쉬운 건 콘티를 통째로 다시 불러오는 것이지만, 그러면 목록을 새로 만들며 각 항목의 내부 키(uid)가 새로 생겨 접어 둔 그룹이 펴지고 골라 둔 선택이 풀린다. 그래서 콘티에 담긴 곡들만 다시 읽어 `item.song`만 교체하고, 항목의 uid·배치·착석은 그대로 뒀다.

```ts
// 곡 편집·삭제·검수가 끝나면 호출 — 곡 id만 다시 읽어 갈아끼운다(uid 유지)
setItems((prev) =>
  prev.map((i) => (i.type === "song" && fresh.has(i.song.id) ? { ...i, song: fresh.get(i.song.id) } : i)),
);
```

전체를 새로 그리는 대신 바뀐 부분만 갈아끼우면, 화면 상태(접힘·선택)를 잃지 않는다.

## 요약

- 예약만 돼 있는 컬럼을 살릴 땐 읽기·저장·복사·모델·내보내기 길을 다 이어야 반쯤 동작을 피한다. 복사 경로를 빠뜨리기 쉽다.
- "전부 지우고 다시 넣는" 저장에선 항목별 소유값(작성자 등)이 통째 저장마다 날아갈 수 있다 — 화면이 왕복시켜 지키고, 고친 항목만 갱신한다.
- 순서를 바꾸는 기능은 스타일 같은 부가 데이터가 "출력 위치"가 아니라 "원본"을 따라가게 원본 번호를 함께 들고 다녀야 한다.
- 인덱스만으론 구조 변화를 다 못 잡는다. 저장 시점의 구조 스냅샷(개수 등)을 함께 두면 증가·감소를 모두 감지한다.
- 일부만 바뀐 화면은 통째로 리로드하지 말고 바뀐 조각만 갈아끼워 상태(접힘·선택)를 지킨다.
