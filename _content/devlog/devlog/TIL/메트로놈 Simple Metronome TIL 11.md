## 콜드스타트 램프업 — 첫 소리가 눌리는 이유

### 같은 크기인데 첫 박만 작다 → 위치 문제

재생 시작 때 첫 박만 작게 들렸다. 첫 박과 둘째 박은 버퍼상 소리 크기(gain)가 똑같은데(둘 다 1.0) 첫 박만 작으니, 소리 데이터가 아니라 "버퍼 맨 앞"이라는 위치가 원인이라는 뜻이다. 같은 값이 위치만 다를 때 결과가 다르면, 원인은 데이터 밖에 있다.

### 무음 뒤 첫 소리는 하드웨어가 누른다

무음 상태에서 재생이 시작되면 기기 스피커·앰프가 pop(퍽 소리)을 막으려고 출력을 서서히 올린다(램프업). 그 램프가 끝나기 전에 나온 첫 클릭이 눌린다. 한 번 데워지면 그 뒤론 정상이라 첫 박에만 나타난다. 앱 코드로 조정할 수 있는 게 아니라 출력 경로의 물리적 특성이다.

## 프리롤 워밍업

### 트랙 맨 앞에 안 들리는 소리를 먼저 흘린다

램프업은 신호가 있어야 일어난다. 그래서 실제 클릭 전에, 사람 귀엔 안 들리는 저레벨 노이즈(~150ms)를 트랙 맨 앞에 붙여 경로를 미리 깨운다. 예열이 끝난 뒤 첫 클릭이 나오면 이미 데워진 경로라 눌리지 않는다.

```kotlin
private fun warmupBuffer(): ShortArray {
    val n = (sampleRate * 0.15).toInt()
    val rnd = java.util.Random()
    val peak = 10                         // ±10 ≈ 매우 낮음, 안 들림
    val fadeIn = (sampleRate * 0.010).toInt()
    return ShortArray(n) { i ->
        val env = if (i < fadeIn) i.toDouble() / fadeIn
                  else (n - i).toDouble() / (n - fadeIn)   // 끝으로 갈수록 0
        ((rnd.nextInt(2 * peak + 1) - peak) * env).toInt().toShort()
    }
}
```

### 페이드아웃으로 예열음을 숨긴다

노이즈를 시작은 크게, 끝으로 갈수록 0으로 배치했다. 이유가 있다 — 시작의 큰 부분은 아직 차가운 앰프가 눌러주니 안 들리고, 앰프가 데워질 무렵엔 노이즈가 이미 0이라 첫 박 직전엔 조용하다. 눌러버리는 하드웨어 특성을 거꾸로 이용해, 예열은 하면서 소리는 숨겼다.

## 예열을 붙이면 소리와 화면이 어긋난다

### 주기 알림은 프레임 0 기준, 클릭은 프리롤만큼 뒤

인디케이터는 오디오 재생 위치의 주기 알림(`setPositionNotificationPeriod`)으로 켜진다. 그런데 이 알림은 "재생 시작(프레임 0)"부터 세고, 실제 클릭은 프리롤만큼 뒤로 밀려 있다. 그대로 두면 소리는 둘째 박인데 불은 첫 박에 뜬다.

### 재생 헤드에서 박 번호를 구한다

박 번호는 재생 헤드 위치(`playbackHeadPosition`, 재생된 프레임 수)를 한 박(subdivision) 길이로 나눠 구한다. 헤드 값은 부호 없는 정수라 오래 재생하면 뒤집힐 수 있어 `and 0xFFFFFFFFL`로 편다.

```kotlin
val head = at.playbackHeadPosition.toLong() and 0xFFFFFFFFL
val idx = (((head + samplesPerSubdiv / 2) / samplesPerSubdiv) % total).toInt()  // 반올림
```

### 점등을 프리롤만큼 지연시켜 맞춘다

알림이 클릭보다 딱 "프리롤 + 리드"만큼 이르다. 그 시간만큼 점등을 미루면(`postDelayed`) 불이 소리와 같은 순간에 뜬다. 첫 클릭은 대응하는 주기 알림이 없어(첫 주기는 한 박 뒤에 뜸) 재생 시작 시점에 직접 지연 점등한다.

```kotlin
val offsetMs = (warmFrames + leadFrames).toLong() * 1000L / sampleRate
mainHandler.postDelayed({
    if (token == playToken) { tickIndex = idx; tickListener?.invoke(idx) }
}, offsetMs)
```

## 왜 "같은 트랙 프리롤"로 귀결했나

예열을 넣는 다른 두 길을 먼저 봤지만 이 기기에서 안 됐다. 둘 다 폐기하고 지금 방식으로 정리했다.

- 별도 예열 트랙: 첫 박은 잡혔으나 재생 때마다 두 번째 오디오 트랙을 만드는 게 간헐 크래시.
- 재생 헤드를 `flush`로 0으로 되돌리는 방식: 예열이 다 나올 때까지 기다리는 로직이 안 끝나 재생이 아예 안 됨.

그래서 예열을 메트로놈 트랙 맨 앞 프리롤로 합치고(트랙 하나), 정렬은 위의 지연 보정으로 처리했다. 기능을 하나 넣을 때 가장 단순한 구조(트랙 하나·부수효과 없음)로 수렴시키는 게, 기기마다 다른 함정을 피하는 길이었다.

## 버퍼가 너무 크면 트랙 생성이 실패한다

BPM 1이면 한 마디가 240초라 한 마디 패턴 버퍼가 ~23MB가 된다. 그 크기를 그대로 오디오 트랙 버퍼로 요청하니 트랙이 안 만들어져 앱이 꺼졌다. 스트리밍 재생(`MODE_STREAM`)은 데이터를 계속 이어 쓰는 방식이라 버퍼가 한 마디를 통째로 담을 필요가 없다.

```kotlin
// 최대 ~4초로 캡 — 정상 BPM엔 영향 없고 느린 BPM 크래시만 막음
val bufBytes = maxOf(minBuf, minOf(pattern.size * 2, sampleRate * 4 * 2))
```

## 요약

- 같은 값이 위치만 달라 결과가 다르면 원인은 데이터 밖이다 — 첫 박 눌림은 무음 뒤 출력 경로가 서서히 켜지는 하드웨어 램프업이었다.
- 램프업은 신호가 있어야 일어나므로, 안 들리는 저레벨 노이즈를 트랙 맨 앞에 프리롤해 경로를 미리 깨운다. 페이드아웃으로 배치하면 차가운 앰프가 초반을 눌러줘 소리는 숨고 예열은 된다.
- 프리롤을 앞에 붙이면 주기 알림(프레임 0 기준)과 클릭이 어긋난다 — 점등을 "프리롤+리드"만큼 지연시켜 맞춘다.
- 기능은 가장 단순한 구조로 수렴시키는 게 기기별 함정(2차 트랙 크래시·flush 재생불가)을 피하는 길이다.
- 스트리밍 버퍼는 재생 단위 전체를 담을 필요가 없다 — 상한을 두지 않으면 극단값에서 트랙 생성이 실패한다.
