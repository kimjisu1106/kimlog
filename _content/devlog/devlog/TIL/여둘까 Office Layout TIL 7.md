회전을 반복하면 배치가 조금씩 풀리고, 되돌리면 반전해 둔 도형이 엉뚱하게 뒤집혔다. 원인은 전부 "화면의 상태와 우리가 적어 둔 상태가 다르다"는 한 가지였다. 그 김에 폼 입력과 파일 드롭에서 밟은 것들도 함께 정리한다.

---

## 변형 뒤에 벌어지는 일

### 변형이 끝나면 Konva가 도형 속성을 다시 계산해 덮어쓴다

Transformer로 회전·크기 조절을 하면, Konva는 새 변환 행렬을 만들어 각 도형에 적용한다. 이때 행렬을 그대로 두는 게 아니라 QR 분해로 위치·회전·배율·기울기로 되돌린 뒤 `setAttrs`로 써넣는다.

```js
const attrs = newLocalTransform.decompose();
node.setAttrs(attrs);
```

분해 방식이 정해져 있어서 결과가 한쪽으로 쏠린다. 가로 배율은 `Math.sqrt(a*a + b*b)`라 언제나 양수가 되고, 거울 반전은 세로 배율의 부호로 몰리며, 회전값이 그만큼 보정된다.

즉 좌우반전 + 0도로 만들어 둔 도형이 회전 한 번에 상하반전 + 180도라는 표현으로 바뀐다. 화면에 보이는 모습은 완전히 같다. 그래서 그 순간에는 아무도 눈치채지 못한다.

---

### 그래서 회전만 받아 적으면 안 된다

우리 코드는 변형이 끝날 때 회전값만 모델에 옮기고 반전 방향은 예전 값을 두었다.

```js
// ❌ 회전만 — 반전 방향이 옛 값으로 남는다
n._fx.rot = n.rotation();

// ✅ 배율 부호까지 함께
n._fx.rot = n.rotation();
n._fx.flipX = n.scaleX() < 0;
n._fx.flipY = n.scaleY() < 0;
```

화면은 새 표현으로 그려져 있는데 모델은 옛 표현이라, 실행취소처럼 모델에서 다시 그리는 순간 다른 그림이 된다. 좌우 대칭인 도형은 티가 안 나고, 위아래가 다른 도형만 뒤집혀 보인다.

라이브러리가 상태를 고쳐 쓸 수 있는 자리에서는 우리가 아는 값을 믿지 말고 그 결과를 통째로 다시 읽어야 한다.

---

### 모델에 반올림해 저장하면 되돌릴 때마다 오차가 쌓인다

회전값을 `Math.round`로 정수화해 저장하고 있었다. 화면은 37.4도인데 기록은 37도다. 되돌리기·축척 보정처럼 기록에서 다시 그리면 그 0.4도가 실제 화면이 되고, 다시 돌리면 또 반올림된다.

한 번은 안 보이지만 그룹을 여러 번 돌리면 도형들이 서로 어긋나기 시작한다.

```js
fx.rot = n.rotation();   // 저장은 실수 그대로
// 표시할 때만
document.getElementById("pR").value = Math.round(selected.rotation());
```

보여주기용 반올림과 저장값을 같은 자리에서 처리하면 안 된다는 것을, 단위 변환 때와 같은 이유로 또 배웠다.

---

### 회전만 해도 배율에 찌꺼기가 남는다

행렬을 분해해 되돌리면 부동소수점 오차로 배율이 1이 아니라 1±0.0000001로 떨어진다. 회전을 반복하면 이게 곱해지며 크기가 조금씩 변한다.

```js
// 크기 변경이 아닌 변형이었다면 배율을 정확한 값으로 되돌린다
n.scaleX(n._fx.flipX ? -1 : 1);
n.scaleY(n._fx.flipY ? -1 : 1);
```

"거의 1"을 그대로 두면 누적된다. 의미상 정확해야 하는 값은 매번 제자리로 돌려놓는 편이 낫다.

---

### 도형을 다시 만들면 맨 앞으로 나온다

크기·속성이 바뀌면 노드를 파괴하고 새로 만드는데, 새 노드는 레이어의 맨 뒤(=화면상 맨 앞)에 붙는다. 바닥에 깔아 둔 방이 크기 조절 한 번에 앞으로 튀어나왔다.

```js
const z = g.zIndex();
g.destroy();
const ng = buildNode(fx);
ng.zIndex(z);
```

겹침 순서를 "자식 배열의 순서"로 관리하고 있다면, 재생성은 곧 순서 변경이라는 것을 기억해야 한다.

---

## 레이어와 히트 판정

### 가려지면 안 되는 표시는 레이어를 나눈다

방 면적 숫자는 그 위에 어떤 가구를 올려도 보여야 한다. 같은 레이어에 두면 겹침 순서 싸움이 끝나지 않는다.

```js
const roomLabelLayer = new Konva.Layer();
stage.add(bgLayer, gridLayer, mainLayer, roomLabelLayer, overlayLayer);
```

레이어를 하나 더 두면 z-order를 다툴 일 자체가 없어진다. 대신 그 표시를 도형과 따로 관리해야 하니, 도형이 움직일 때마다 다시 그려 맞춘다. 개수가 적으면 부분 동기화보다 통째로 다시 만드는 쪽이 실수가 적다.

---

### 투명 채움은 안 보이지만 클릭은 잡힌다

방의 벽을 끄면 안 보여야 하지만, 네 면을 다 끄면 도형을 다시 고를 수 없게 된다. 채움을 투명으로 두면 이 문제가 사라진다.

```js
fill: walls[side] ? fx.color : "transparent"
```

Konva는 히트 판정을 별도 캔버스에 도형을 칠해서 하는데, 이때 알파를 보지 않는다. 그래서 투명하게 칠한 도형도 클릭은 그대로 잡힌다.

---

### findOne은 첫 번째 하나만 집는다

선택 표시는 도형의 몸통에 테두리 색을 칠하는 방식이었다.

```js
const body = n.findOne(".body");   // 방은 벽 네 개가 전부 body — 첫 번째(위쪽 벽)만 집힌다
```

가구는 몸통이 하나라 문제가 없었는데, 몸통이 여럿인 방이 들어오자 위쪽 벽에만 테두리가 남았다. 벽을 꺼서 투명해져도 테두리는 남으니 "안 지워지는 선"으로 보였다.

이름 하나로 여러 자식을 쓰는 구조라면 `findOne`이 아니라 `find`를 쓰거나, 그 종류를 아예 다른 경로로 처리해야 한다.

---

## 폼 입력 함정

### `<input>`은 값에서 줄바꿈을 지운다

여러 줄 텍스트를 넣고 색을 바꿨더니 한 줄로 합쳐졌다. 속성 패널이 값을 바꿀 때마다 이름칸을 읽어 모델에 다시 적고 있었는데, 한 줄 입력칸은 값을 받을 때 줄바꿈을 제거한다(HTML 명세의 값 정리 규칙).

읽어서 다시 쓰는 순간 원본이 손상된다. 여러 줄을 다루는 값은 한 줄 입력칸을 거치게 두면 안 된다 — 읽지 않거나, 아예 읽기 전용으로 막는다.

---

### label로 감싸면 글자를 눌러도 체크박스가 켜진다

이름 옆에 "도형에 표시" 체크를 붙이면서, 줄 전체를 `<label>`로 감쌌더니 "이름"이라는 글자를 눌러도 체크가 토글됐다. `for`를 안 줘도 label 안의 첫 입력 요소가 그 label의 대상이 되기 때문이다.

```html
<div class="row-head"><span>이름</span>
  <label class="check-inline"><input type="checkbox" id="pShowName"> 도형에 표시</label>
</div>
```

바깥은 `div`로 두고 체크박스만 label로 감싼다.

---

### 전역 단축키 가드에 textarea도 넣어야 한다

Delete로 선택한 도형을 지우는 단축키가 있는데, 가드가 `INPUT`만 보고 있었다. 여러 줄 입력 상자를 새로 만들자 글을 지우려 누른 Delete가 캔버스의 도형을 지웠다.

```js
if (e.target.tagName === "INPUT" || e.target.tagName === "TEXTAREA") return;
```

입력 요소를 새로 추가할 때는 전역 키 핸들러의 가드를 함께 점검해야 한다.

---

## 파일 다루기

### 파일 드롭은 dataTransfer.types로 가른다

팔레트에서 가구를 끌어다 놓는 동작이 이미 드래그앤드롭을 쓰고 있어서, 파일 드롭을 얹으면 서로 걸린다. 실제 파일이 실린 드래그인지 먼저 본다.

```js
const hasFile = (e) => Array.from(e.dataTransfer.types || []).includes("Files");
```

앱 안에서 시작한 드래그에는 `Files`가 없다. 이 한 줄로 두 동작이 안 부딪힌다.

---

### dragover에서 막지 않으면 브라우저가 파일을 열어버린다

`drop`만 처리하면 아무 일도 일어나지 않는다. 브라우저의 기본 동작은 "이 파일을 새 탭에서 연다"이고, 그걸 막는 자리는 `dragover`다.

```js
window.addEventListener("dragover", (e) => { if (hasFile(e)) e.preventDefault(); });
```

`drop`에서도 다시 막아야 한다. 둘 중 하나만 막으면 페이지가 파일로 대체된다.

---

### 웹앱에 파일을 연결하려면 설치가 필요하다

"파일을 더블클릭하면 이 웹앱이 열리게 할 수 있나"를 알아봤다. 웹페이지 자체는 운영체제의 파일 연결을 가져갈 수 없다. 방법은 하나뿐이다.

- 매니페스트에 `file_handlers`로 확장자를 적고
- 사용자가 브라우저에서 앱으로 설치하면
- 실행 시 `launchQueue`로 넘어온 파일을 받는다

크로미움 계열에서만 되고, 사용자가 한 번은 설치해야 한다. "웹으로 되냐"의 답이 "설치하면 된다"인 경우라, 그 비용을 감당할 만한지부터 정하는 게 순서였다.

---

### 윈도우 파일 아이콘은 확장자를 등록하면 바뀐다

앱 설치 없이 아이콘만 붙이는 것은 레지스트리로 된다. 관리자 권한도 필요 없다.

```text
[HKEY_CURRENT_USER\Software\Classes\.ol]
@="OfficeLayout.Plan"

[HKEY_CURRENT_USER\Software\Classes\OfficeLayout.Plan\DefaultIcon]
@="C:\...\ol-file.ico"
```

확장자를 형식 이름에 연결하고, 그 형식에 아이콘을 달아주는 구조다. 열리는 프로그램을 지정하지 않으면 아이콘만 바뀌고 더블클릭은 여전히 "연결 프로그램 선택"이 뜬다.

---

### 작은 아이콘은 같은 그림을 줄이면 안 된다

256px에서 멀쩡하던 마크가 32px에서는 뭉개지고 16px에서는 얼룩이 된다. 크기마다 담는 양을 다르게 했다.

- 64px 이상은 여백을 두고 마크 전체를
- 32·48px은 더 당겨 마크가 타일을 채우게
- 16px은 아예 단순한 형태(테두리 원과 십자)로 다시 그려서

하나의 그림을 여섯 크기로 줄이는 게 아니라, 크기별로 다른 그림을 담는 것이 아이콘 파일의 원래 용도였다.
